## Виртуализация
**Виртуализация** - предоставление набора вычислительных ресурсов, абстрагированное от аппаратной реализации и обеспечивающее при этом изоляцию друг от друга вычислительных процессов, выполняемых на одном компьютере
- Полная эмуляция операционной системы
- Тяжеловесные (ГБ)
- Медленный запуск (минуты)
- Собственное ядро ОС
- Полная изоляция
- Меньшая производительность
- Примеры: VirtualBox, VMware

**Контейнеризация** - вид виртуализации
- Работает поверх операционной системы хоста
- Легковесные (МБ)
- Быстрый запуск (секунды)
- Общее ядро ОС
- Меньше изоляции
- Высокая производительность
- Примеры: Docker, Podman

Основное различие - уровень изоляции и эффективность использования ресурсов.

## Infrastructure as Code
### Определение
**Определение от гопоты**: Методология управления и предоставления инфраструктуры через машиночитаемые определения, а не через физические аппаратные настройки или интерактивные инструменты конфигурации.
**Определение с [сайта](https://developer.hashicorp.com/terraform/tutorials/docker-get-started/infrastructure-as-code) Terraform**: набор технологий, позволяющий управлять инфраструктурой при помощи конфигурационных файлов вместо гуя

Ключевые **преимущества** Infrastructure as Code:
- Описание инфраструктуры в виде кода позволяет точно и многократно воссоздавать **идентичные среды**. Больше не нужно выполнять ручную настройку серверов - достаточно запустить скрипт или манифест.
- Код инфраструктуры может храниться в **системах контроля версий** (Git), что обеспечивает:
     - Отслеживание изменений
     - Возможность отката к предыдущим конфигурациям
     - Коллаборацию команды разработчиков
- **Автоматизация** IaC позволяет автоматизировать процессы развертывания и конфигурирования через:
     - Непрерывную интеграцию
     - Непрерывное развертывание
     - Автоматические тесты инфраструктуры

### Terraform
Открытый инструмент от HashiCorp для декларативного описания облачной инфраструктуры. Ключевые особенности:

Основные характеристики:
- [Поддержка](https://registry.terraform.io/browse/providers?product_intent=terraform) как многих облачных провайдеров (AWS, Azure, Google Cloud), так и локального развёртывания (Docker)
- Декларативное описание инфраструктуры (описывается желаемое состояние системы, и Terraform сам высчитывает нужные зависимости, количество ресурсов, контейнеров, ...)
- Язык конфигурации HCL (HashiCorp Configuration Language)
- Создание планов выполнения перед применением изменений

Пример конфигурации Terraform:
```hcl
provider "aws" {
  region = "us-west-2"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  
  tags = {
    Name = "WebServer"
  }
}
```

Workflow Terraform:
1. Init - инициализация провайдеров
2. Plan - генерация плана изменений
3. Apply - применение конфигурации
4. Destroy - удаление инфраструктуры

#### Ориентировочная структура проекта
- `main.tf` — основной файл с описанием ресурсов.
- `variables.tf` — определение переменных.
- `outputs.tf` — вывод значений (например, IP-адресов, имен ресурсов).
- `providers.tf` — настройка провайдеров (AWS, GCP, Azure и т.д.).
- `modules/` — директория для модулей, которые можно переиспользовать.

#### Организация multi-environment project
Для управления несколькими окружениями (dev, staging, production) можно использовать следующие подходы:

**Разделение по директориям**:
- Каждое окружение находится в отдельной директории (например, `environments/dev`, `environments/staging`, `environments/prod`).
- В каждой директории свои `terraform.tfvars` и конфигурации.
- Пример структуры:
```
terraform/
├── environments/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   ├── staging/
│   └── prod/
├── modules/
│   ├── vpc/
│   ├── ec2/
│   └── rds/
```

**Использование Terraform Workspaces**:
- Workspaces позволяют использовать одно и то же состояние (state) для разных окружений. Пример:
```bash
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod
```
- Переключение между workspace:
```bash
terraform workspace select dev
```
- Workspaces подходят для небольших проектов, но могут усложнить управление состоянием в крупных проектах.

**Использование отдельных состояний (state) для каждого окружения**:
- Каждое окружение имеет свой бэкенд (например, S3 bucket для AWS) и состояние.
- Это обеспечивает изоляцию и безопасность.

#### Лучшие практики по использованию многих Terraform states
- **Изоляция окружений**: используйте отдельные состояния для каждого окружения (dev, staging, prod). Это предотвращает случайное воздействие на production.
- **Использование Remote Backend**: храните состояние в удаленном бэкенде (например, S3, Azure Storage, Terraform Cloud). Это обеспечивает:
     - Безопасность (доступ только для авторизованных пользователей).
     - Совместную работу команды.
     - Блокировку состояния для предотвращения конфликтов.
- **Модулизация**: разделяйте инфраструктуру на модули (например, VPC, EC2, RDS). Это упрощает переиспользование и управление.
- **Использование переменных и `terraform.tfvars`**: Определяйте переменные для настройки окружений. Например:
```hcl
variable "environment" {
  type = string
}
```
- **Ограничение доступа к состояниям**: настройте права доступа к бэкенду (например, IAM-роли в AWS) так, чтобы только определенные пользователи могли изменять production-состояние.
- Если вам нужно использовать выходные данные из одного состояния в другом, **используйте `terraform_remote_state`**:
```hcl
data "terraform_remote_state" "vpc" {
  backend = "s3"
  config = {
    bucket = "my-terraform-state"
    key    = "vpc/terraform.tfstate"
    region = "us-east-1"
  }
}
```
- **Интегрируйте Terraform с CI/CD** (например, Jenkins, GitLab CI, GitHub Actions) для автоматического применения изменений.
- **Планирование и проверка**: всегда используйте `terraform plan` перед `terraform apply`, чтобы убедиться в корректности изменений.
- **Включите версионирование** в бэкенде (например, S3 bucket versioning), чтобы иметь возможность отката состояний.
- Для крупных проектов **используйте политики** (например, Sentinel в Terraform Cloud/Enterprise или Open Policy Agent) для контроля изменений.

#### Docker nginx container deploy
1. Есть файл `terraform.tf`, определяющий версии Terraform и провайдера, которые будут использоваться
```hcl
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0.2"
    }
  }
  required_version = "~> 1.7"
}
```

2. Есть файл `main.tf`, описывающий *желаемое состояние системы* (вообще [пишут](https://habr.com/ru/companies/otus/articles/696694/), что можно хоть всю конфигурацию в один файл запихнуть)
```hcl
provider "docker" {}
resource "docker_image" "nginx" {
     name         = "nginx:latest"
     keep_locally = false
}
resource "docker_container" "nginx" {
     image = docker_image.nginx.image_id
     name  = "tutorial"
     ports {
          internal = 80
          external = 8000
     }
}
```

3. В терминале выполняется `terraform init` и `terraform apply` (нужно будет ввести `yes`). Также желательно выполнить `terraform plan`, чтобы проверить, то ли, что нужно, Terraform будет выполнять
4. Terraform поднимает nginx контейнер со случайным названием в докере
5. Для удаления инфраструктуры нужно выполнить `terraform destroy` (`yes`)

### Ansible
Инструмент автоматизации от Red Hat, который используется для удалённого конфигурационного управления, оркестрации и развертывания приложений.
[Статья на хабре](https://habr.com/ru/companies/selectel/articles/196620/) (поздно заметил, что ей так-то больше 10 лет)

Ключевые особенности Ansible:
- на управляемые узлы не нужно устанавливать никакого дополнительного ПО, **всё работает через SSH**
- код программы, написанный на Python, очень прост; при необходимости **написание дополнительных модулей не составляет особого труда**;
- **язык**, на котором пишутся сценарии, также **предельно прост**;
- низкий порог вхождения: обучиться работе с Ansible можно за очень короткое время;
- документация к продукту написана очень подробно и вместе с тем — просто и понятно; она регулярно обновляется;
- Ansible работает не только в режиме push, но и pull, как это делают большинство систем управления (Puppet, Chef);
- имеется возможность последовательного обновления состояния узлов (**rolling update**).

Пример плейбука Ansible:
```yaml
- hosts: webservers
  become: yes
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
    
    - name: Start nginx
      service:
        name: nginx
        state: started
```

Особенности плейбуков:
- `hosts` указывает узлы или группы узлов, к которым нужно применить изменения
- `tasks` описывает конечное состояние узлов
- Перед запуском задач можно указать следующие параметры:
     - собирать ли информацию о хостах (`gather_facts`, по умолчанию да)
     - переменные (`vars`); также можно указать переменные, значения которых будут уточнены у пользователя в интерактивном режиме перед выполнением, при помощи `vars_prompt`
     - метод соединения с хостами (`connection`: `pure ssh`, `chroot`, `jail`, `local`, ...)
     - под каким пользователем выполнять задачу (`sudo: <yes|no>`, по умолчанию, как нетрудно догадаться, другой пользователь - это root. Имя другого пользователя указывается при помощи `user`)
     - имя пользователя для аутентификации на удалённом хосте (`remote_user`, в предыдущих версиях - просто `user`. *И я хз, как это соотносится с тем, что пример с `sudo` в статье на хабре использует `user`. Может, там версия старая, а может, это два разных параметра*)
- Каждую задачу можно выполнять под разными пользователями
- Доступно условное выполнение команд при помощи параметров `register` (устанавливает переменную) и `when` (выполняет задачу по условию, например, если значение переменной изменилось)

[Основные компоненты Ansible](https://docs.ansible.com/ansible/latest/getting_started/basic_concepts.html):
- Inventory - список управляемых хостов
- Playbooks - сценарии выполнения задач
- Modules - стандартные блоки для выполнения операций
- Roles - переиспользуемые наборы задач

### Различия Terraform и Ansible:
Terraform:
- Декларативное описание инфраструктуры
- Фокус на создании облачных ресурсов
- Состояние инфраструктуры
- Мультиоблачность

Ansible:
- Конфигурационное управление
- Установка и настройка ПО
- Выполнение задач на серверах
- Оркестрация приложений

Современные подходы часто предполагают совместное использование этих инструментов:
- Terraform для создания инфраструктуры
- Ansible для конфигурирования и деплоя приложений

### Terraform vs CloudFormation
Преимущества CloudFormation
- **Полная интеграция с AWS**. Поддержка новых сервисов и фич появляется быстрее, чем в Terraform.
- Позволяет **управлять ресурсами через AWS-сервисы** (например, использовать Lambda и API Gateway)
- **Автоматическая обработка зависимостей** (CloudFormation сам определяет порядок создания/удаления ресурсов, что упрощает написание шаблонов)
- Более высокий уровень **безопасности и контроля**

Преимущества Terraform
- **Поддержка различных платформ** (сотни провайдеров, включая Kubernetes, GitHub, Snowflake)
- **Модульность и переиспользование кода**. Даёт возможность создавать модули и использовать их в разных проектах (например, модуль VPC для AWS). Огромная экосистема готовых модулей в Terraform Registry (например, модуль EKS от AWS).
- **Гибкость управления состоянием**. Состояние (state) хранится в удаленном бэкенде (S3, Terraform Cloud) с блокировкой для предотвращения конфликтов. Можно импортировать существующие ресурсы в состояние (`terraform import`).
- **Расширенный CI/CD**. Легко интегрируется с любыми инструментами CI/CD (GitLab CI, GitHub Actions, Jenkins). Поддерживает Workspaces для управления разными окружениями (dev, staging, prod).

| **Критерий**                     | **CloudFormation**                           | **Terraform**                              |
| -------------------------------- | -------------------------------------------- | ------------------------------------------ |
| **Поддержка облаков**            | Только AWS.                                  | AWS, GCP, Azure, Kubernetes и другие.      |
| **Синтаксис**                    | YAML/JSON (более многословный).              | HCL (лаконичный и читаемый).               |
| **state**                        | Управляется AWS (невидимо для пользователя). | Явное управление через `.tfstate`-файлы.   |
| **Модульность**                  | Ограничена (вложенные стеки).                | Высокая (переиспользуемые модули).         |
| **Интеграция с CI/CD**           | Требует AWS-специфичных инструментов.        | Универсальная (любой CI/CD).               |
| **Поддержка сообщества**         | Официальная документация AWS.                | Большое сообщество + Terraform Registry.   |
| **Импорт существующих ресурсов** | Частичная поддержка.                         | Полная поддержка через `terraform import`. |
Итого:
- **CloudFormation**, если есть завязка на AWS и её новейшие фичи
- **Terraform**, если нужна мультиоблачность, модульность или гибкость в управлении инфраструктурой

## Шляпа
### Артефакт
... в контексте разработки программного обеспечения - это результат процесса сборки, который может быть развернут или установлен. Это может быть скомпилированный код, библиотека, исполняемый файл, Docker-образ или пакет. Артефакт представляет собой конкретный, готовый к использованию продукт, который создается в результате компиляции, сборки или упаковки исходного кода.

### GitOps
... - методология управления инфраструктурой и конфигурацией с использованием Git в качестве единственного источника истины. Основная идея заключается в том, что состояние инфраструктуры и приложений полностью описывается в Git-репозитории, а все изменения происходят через pull request'ы и автоматические процессы.

Преимущества GitOps:
- Декларативное описание инфраструктуры
- Версионность всех изменений
- Простота отслеживания и аудита
- Автоматизация процессов деплоя
- Повышенная безопасность через контроль изменений
- Легкость отката к предыдущим состояниям

Недостатки GitOps:
- Сложность первоначальной настройки
- Необходимость высокой культуры разработки
- Дополнительные накладные расходы на синхронизацию
- Риски при неправильной настройке CI/CD
- Требует глубоких знаний инструментов

### Есть два бренча: dev и stage. Мы забросили Dockerfile в dev, а затем сбилдили в dev и stage. Это будет одним артефактом или разными?
Если Dockerfile и исходный код идентичны в обеих ветках (dev и stage)
- **Артефакт будет один и тот же**, если:
     - Вы собираете образ из одного и того же коммита (например, после мержа ветки `dev` в `stage`).
     - Ветка `stage` содержит актуальную версию Dockerfile и кода из `dev`.
     - Контекст сборки (файлы, зависимости) не меняется между сборками.
- Docker использует слои, и если входные данные (Dockerfile, контекст) идентичны, хеш образа будет совпадать.

Если ветки dev и stage имеют различия
- **Артефакты будут разными**, если:
    - Ветка `stage` не получила последние изменения из `dev` (например, Dockerfile или код приложения отличается).
    - В процессе сборки используются переменные окружения, которые различаются между `dev` и `stage` (например, `ENV APP_ENV=dev` vs `ENV APP_ENV=stage`).
    - Ветки содержат разные версии зависимостей (например, `package.json` или `requirements.txt`).

Как избежать проблем и гарантировать консистентность
- **Стратегия продвижения артефактов (Build once, deploy everywhere)**:
    - Соберите образ **один раз** в `dev`, протестируйте его.
    - Используйте **тот же самый образ** (с тем же тегом) для деплоя в `stage` и далее в `prod`.
    - Пример тега: `my-app:1.0.0-<commit-hash>`.
- **Автоматический мерж веток**:
    - Настройте CI/CD так, чтобы изменения из `dev` автоматически мержились в `stage` после успешных тестов.
    - Это гарантирует, что `stage` всегда использует актуальный код.
- **Использование единого контекста**:
    - Убедитесь, что сборка выполняется из одного и того же контекста (например, из тега репозитория, а не ветки).
- **Проверка хеша образа**:
    - Docker-образы имеют уникальный хеш (SHA256). Сравните хеши образов для `dev` и `stage`, чтобы убедиться в идентичности:

```bash
docker inspect my-app:dev --format '{{.Id}}'
docker inspect my-app:stage --format '{{.Id}}'
```

- **Плохая практика**:
    - Сборка образа в `dev`, затем повторная сборка в `stage` из своей ветки (где код может отличаться).
    - Результат: два разных образа, возможные баги в `stage`.
- **Хорошая практика**:
    - Сборка образа в `dev` → тестирование → продвижение этого же образа в `stage` через CI/CD.
    - Результат: один артефакт, прошедший все стадии.

### Какие стадии должны быть в любом пайплайне?
В любом CI/CD пайплайне обычно присутствуют следующие стадии:
1. **Lint** — проверка кода на соответствие стандартам и стилю. Это помогает избегать ошибок, связанных с синтаксисом и форматированием.
2. **Unit Testing** — запуск модульных тестов для проверки корректности работы отдельных компонентов приложения.
3. **Integration Testing** — тестирование взаимодействия между различными модулями или сервисами.
4. **Build** — сборка приложения (компиляция, упаковка в артефакты и т.д.).
5. **Security Scanning** — проверка кода и зависимостей на уязвимости (например, с помощью инструментов вроде Snyk, OWASP Dependency-Check).
6. **Artifact Storage** — сохранение собранных артефактов в репозиторий (например, Nexus, Artifactory, S3).
7. **Deploy to Staging** — развертывание на тестовую среду для дальнейшего тестирования.
8. **End-to-End (E2E) Testing** — тестирование всего приложения в среде, максимально приближенной к production.
9. **Deploy to Production** — развертывание на production-среду.
10. **Smoke Testing** — проверка работоспособности приложения после деплоя.
11. **Rollback** — автоматический откат в случае неудачного деплоя (опционально, но рекомендуется).

## Определения
**Облачный сервис** - сервис, предоставляющий инфраструктуру/платформу/ПО по требованию через Интернет, имеющий возможность масштабирования по требованию, требующий оплату по факту использования.
Основывается на кластеризации физических ресурсов: много серверов объединяются вместе, и уже из кластера условно нарезается тысяча виртуалок по одному ядру.

**Тенант** - лицо (физическое или юридическое), подписавшееся на услуги облачного провайдера и пользующееся этими услугами. Услугами может выступать инфраструктура (вирутальные машины, площадки развёртывания контейнеров, ...), хранилища данных, ПО и т.д. Тенанты разделяют эти ресурсы в изолированном окружении (по умолчанию из одного тенанта нельзя получить доступ в другой)

## aaS
### IaaS
Инфраструктура как сервис предоставляет пользователям виртуализированные вычислительные ресурсы через интернет. Это включает в себя виртуальные машины, хранилище, сети и другие компоненты инфраструктуры. Пользователи могут развертывать и управлять операционными системами и приложениями на этих виртуальных машинах, но при этом они не несут ответственности за физическую инфраструктуру, такую как серверы и сети.

Преимущества IaaS включают гибкость, масштабируемость и возможность платить только за использованные ресурсы. Примеры IaaS-провайдеров включают Amazon Web Services (AWS), Microsoft Azure и Google Cloud Platform (GCP).

### PaaS
Платформа как сервис предоставляет пользователям платформу для разработки, тестирования и развертывания приложений без необходимости управлять базовой инфраструктурой. PaaS включает в себя все необходимые инструменты и сервисы, такие как базы данных, серверы приложений, инструменты разработки и интеграции, а также средства для управления жизненным циклом приложений.

С помощью PaaS разработчики могут сосредоточиться на написании кода и создании приложений, не беспокоясь о настройке и управлении серверным оборудованием или операционными системами. Примеры PaaS-провайдеров включают Heroku, Google App Engine и Microsoft Azure App Service.

### SaaS
ПО как сервис предоставляет пользователям доступ к программному обеспечению через интернет. В отличие от IaaS и PaaS, где пользователи управляют своими собственными приложениями и инфраструктурой, в SaaS пользователи просто используют готовые приложения, которые хранятся и управляются провайдером.

SaaS-решения обычно доступны через веб-браузер и требуют минимальной настройки со стороны пользователя. Примеры SaaS-приложений включают Google Workspace, Microsoft 365, Salesforce и Dropbox.

### Отличия между IaaS, PaaS и SaaS
**Уровень управления** (падает слева направо):
- В IaaS пользователи управляют виртуальными машинами и операционными системами, а также могут устанавливать и настраивать приложения.
- В PaaS пользователи управляют только приложениями и данными, в то время как провайдер управляет платформой и инфраструктурой.
- В SaaS пользователи не управляют ни приложениями, ни инфраструктурой; они просто используют готовое программное обеспечение.

## Аналоги AWS Lambda в других облачных платформах
- Google Cloud Platform:
     - **Cloud Functions** - прямой аналог Lambda: событийно-ориентированные функции с автоматическим масштабированием. Интегрируется с другими сервисами гуглового облака (Cloud Storage, Pub/Sub, Firestore).
     - **Cloud Run** предназначен для запуска контейнеризированных приложений с бессерверным масштабированием. Подходит для долгих задач и больших зависимостей (*до 4 ГБ памяти, 60 минут выполнения*).
- Kubernetes:
     - **Knative** - бессерверный фреймворк для Kubernetes. Поддерживает автоматическое масштабирование до нуля (если нет запросов). Например, позволяет запускать функции и микросервисы в кластере k8s
     - **Kubernetes Jobs/CronJobs** предназначен для периодических задач с фиксированным временем выполнения. Например, для ежедневной синхронизации данных между системами
     - **KEDA** (Kubernetes Event-Driven Autoscaling) - инструмент для автоматического масштабирование подов на основе событий (например, из Kafka, RabbitMQ)

### CloudWatch
**Amazon CloudWatch** — это сервис мониторинга от AWS, который позволяет собирать, анализировать и визуализировать метрики, логи и события в реальном времени. Он используется для мониторинга ресурсов AWS, приложений и инфраструктуры.

**Основные функции** CloudWatch:
- **Сбор метрик**:
     - Автоматически собирает метрики для сервисов AWS (например, EC2, RDS, Lambda, S3).
     - Позволяет публиковать кастомные метрики (например, метрики приложения).
- **Мониторинг инфраструктуры**:
     - Мониторинг CPU, памяти, дискового пространства, сетевого трафика и других показателей.
     - Пример: Мониторинг загрузки CPU инстанса EC2.
- **Сбор и анализ логов**:
     - Централизованное хранение логов (например, логи приложений, системные логи).
     - Возможность поиска и фильтрации логов с помощью CloudWatch Logs Insights.
- **Алертинг**:
     - Настройка уведомлений (например, через SNS) при превышении пороговых значений метрик.
     - Пример: Уведомление, если загрузка CPU превышает 80%.
- **Автоматизация**:
     - Запуск действий (например, Auto Scaling, Lambda-функции) на основе метрик или событий.
     - Пример: Автоматическое добавление инстансов EC2 при высокой нагрузке.
- **Дашборды**:
     - Создание пользовательских дашбордов для визуализации метрик и логов.
- **Трассировка (X-Ray)**:
     - Интеграция с AWS X-Ray для анализа производительности распределенных приложений.
- **События (Events)**:
     - Реагирование на изменения в инфраструктуре (например, запуск или остановка инстанса EC2).

**Пример использования**:
- Мониторинг производительности веб-приложения (загрузка CPU, количество запросов, ошибки).
- Настройка оповещений при недоступности сервиса.
- Анализ логов для поиска ошибок.

### Разница между частными и публичными сетями
В AWS сети организуются с использованием **VPC (Virtual Private Cloud)**. Внутри VPC можно создавать **публичные** и **частные** подсети, которые отличаются доступностью ресурсов из интернета.

| **Аспект**              | **Публичная подсеть**                           | **Частная подсеть**                     |
| ----------------------- | ----------------------------------------------- | --------------------------------------- |
| **Доступ из интернета** | Да (через интернет-шлюз).                       | Нет (только через NAT Gateway или VPN). |
| **Публичные IP-адреса** | Могут быть назначены.                           | Не назначаются.                         |
| **Безопасность**        | Менее безопасна, так как доступна из интернета. | Более безопасна, так как изолирована.   |
| **Использование**       | Веб-серверы, балансировщики нагрузки.           | Базы данных, внутренние сервисы.        |

### Lambda
AWS Lambda — это сервис бессерверных вычислений, который позволяет запускать код без управления инфраструктурой.  

**Преимущества:**
- Автоматическое масштабирование:
- Экономия на инфраструктуре (платите только за время выполнения (*цена за миллисекунды*))

**Когда использовать**:
- Событийно-ориентированные задачи:
    - Обработка событий от сервисов AWS (S3, DynamoDB, SQS, Kinesis и т.д.). Например, автоматическая генерация миниатюр изображений при загрузке в S3.
    - Реакция на HTTP-запросы через API Gateway (REST/WebSocket API). Например, бэкенд для мобильного приложения.
-  Короткие и периодические задачи (с временем выполнения *до 15 минут*). Например, ежедневная очистка временных данных, обработка данных из Cron-задач (через CloudWatch Events).
- Микросервисы и легковесные приложения. Например, аутентификация пользователей, верификация токенов

**Когда не стоит использовать**
- Долгие задачи
- Постоянные соединения: Lambda не подходит для долгих сессий (например, WebSocket с постоянным подключением). Вместо этого стоит использовать EC2, ECS/Fargate или специализированные сервисы (например, AWS AppSync для WebSocket).
- Высокопроизводительные вычисления (тренировка ML-моделей, например): есть ограничения по памяти (*до 10 ГБ*) и CPU (*выделяется пропорционально памяти*)
- Большие зависимости: Максимальный размер развертываемого пакета (ZIP-архив + слои) ограничен *250 МБ*. Пример: приложения с тяжелыми библиотеками. Вместо этого стоит использовать контейнеры
- В случаях, требующих мгновенного отклика (например, реальный трейдинг), т.е. при холодном старте. Вместо этого стоит использовать Provisioned Concurrency в Lambda или перейти на ECS/Fargate.

# CI/CD
## Определение
**CI/CD** (Continuous Integration/Continuous Delivery) - это методология автоматизации процессов разработки, тестирования и развертывания программного обеспечения

### Этапы CI/CD:
- **Написание кода**
     - Написание функционала
     - Создание feature-веток
     - Код-ревью
- **Continuous Integration** (CI) - практика частого слияния изменений разработчиков в центральный репозиторий с последующей автоматической сборкой и тестированием
     - Много изменений (коммитов) в день
     - Автоматическая сборка кода
     - Статический анализ
     - Автотесты (unit- и интеграционные)
     - Быстрая обратная связь
- **Continuous Delivery** (CD) - подход к разработке программного обеспечения, при котором команда производит ПО в коротких циклах, гарантируя, что код всегда находится в состоянии, пригодном для развертывания
     - Автоматизация релизов:
          - Подготовка артефактов
          - Деплой в тестовые среды
          - Приёмочное тестирование
     - Ручное подтверждение релиза
     - Возможность отката
- **Continuous Deployment** - следующий уровень после Continuous Delivery, когда релиз происходит автоматически после прохождения всех тестов
     - Автоматический деплой в продакшен
     - Мониторинг работоспособности
     - Автоматический откат при проблемах
     - Отличия от CD:
          - Полная автоматизация релиза
          - Никаких ручных подтверждений
          - Мгновенное попадание в продакшен

Разница между CD и Continuous Deployment:
Continuous Delivery:
- Код готов к релизу
- Финальное решение за человеком
- Ручной деплой
- Больше контроля

Continuous Deployment:
- Автоматический релиз
- Никаких ручных действий
- Мгновенное попадание в продакшен
- Высокая скорость внедрения

## Стратегии развёртывания
- **Rolling Update** - наиболее распространенная и консервативной стратегия. Суть подхода заключается в последовательном обновлении компонентов системы без полной остановки сервиса. При использовании Rolling Update система заменяет серверы постепенно, что позволяет сохранять работоспособность всего приложения.
- При **Blue-Green Deployment** создаются две абсолютно идентичные среды - синяя (текущая рабочая версия) и зеленая (новая версия). Вся инфраструктура дублируется, что дает возможность полностью протестировать новую версию без риска для производственной среды. В момент готовности происходит мгновенное переключение всего трафика, как будто опускается занавес и начинается новое представление (аналогия - генеральная репетиция в театре).
- **Canary Deployment** заключается в проверке работоспособности новой версии на малой доле реального трафика, которая впоследствии увеличивается, если ошибок не обнаруживается.
- **Recreate Strategy** представляет собой наиболее простой и грубый метод обновления. Происходит полная остановка существующей версии, после чего разворачивается новая. Такой подход неизбежно приводит к временной недоступности сервиса, что критично для систем, требующих высокой отказоустойчивости.
- **Shadow Deployment** заключается в том, что две системы работают параллельно, и часть трафика основной системы передаётся новой системе. Таким образом проверяется её работоспособность без влияния на реальных пользователей
- **A/B Testing** (*полагаю, что это можно даже не указывать, потому что это не именно стратегия развёртывания*) выходит за рамки классического деплоя и превращается в полноценный инструмент исследования. Параллельно запускаются две версии системы с незначительными отличиями, после чего собираются и анализируются метрики производительности, удобства использования или конверсии.

# Docker
## База
**Docker** - это платформа для контейнеризации приложений, которая позволяет:
- Упаковывать приложение и все его зависимости в изолированный контейнер
- Обеспечивать единообразие среды разработки и продакшена
- Быстро разворачивать и масштабировать приложения
- Эффективно использовать системные ресурсы

**Docker Best Practices**:
- Минимализация образов Docker:
     - Использовать официальные легковесные базовые образы (alpine, slim)
     - Удалять менеджеры пакетов и кэш после установки
     - Использовать многоступенчатую сборку (multi-stage build)
     - Минимизировать количество слоев
Пример оптимального Dockerfile:
```dockerfile
FROM python:3.9-alpine
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```
- Управление зависимостями:
     - Фиксировать точные версии библиотек
     - Использовать requirements.txt
     - Проверять уязвимости зависимостей
- Безопасность:
     - Не использовать root-пользователя
     - Применять принцип наименьших привилегий
     - Использовать механизмы секретов (==аргументы, переменные окружения, так?==)
     - Сканировать образы на уязвимости
- Эффективность кэширования:
     - Располагать слои от редко меняющихся к часто меняющимся
     - Копировать только необходимые файлы
     - Использовать .dockerignore
- Управление конфигурацией:
     - Использовать ENV переменные
     - Применять Docker Compose
     - Экстернализировать конфигурации
- Логирование и мониторинг:
     - Логировать в stdout/stderr
     - Использовать centralized logging
     - Интеграция с ELK, Prometheus
- CI/CD:
     - Автоматизация сборки образов
     - Интеграция с GitLab/GitHub Actions
     - Автоматическое тестирование образов
     - Деплой через Kubernetes/Docker Swarm

**Docker Compose**
- Инструмент для определения и запуска многоконтейнерных приложений
- Позволяет конфигурировать сервисы через YAML-файл
- Управляет несколькими контейнерами как единым приложением

**Docker CLI** - командный интерфейс для работы с Docker. Основные команды:
```bash
docker ps           # список контейнеров
docker images       # список образов
docker build        # сборка образа
docker run          # запуск контейнера
docker stop         # остановка
docker rm           # удаление
docker exec         # выполнение команд внутри
```

**Docker in Docker (DinD)**
- Запуск Docker внутри Docker-контейнера
- Используется для:
    - При построении пайплайна CI/CD в GitLab или Jenkins для создания образов Docker и их публикации в registry (реестре образов)
     - При использовании Jenkins Dynamic Agents (динамических Docker-контейнеров) 
     - При необходимости построения изолированной среды от хоста, где будет выполнятся стендовая работа, а после проведения можно будет легко удалить её.
- Способы:
     - Запуск docker путём монтирования docker.sock (метод DooD)
     - Использовать дочерний контейнер внутри контейнера (метод dind)
     - Использование среды выполнения Nestybox sysbox Docker

**Multistage Build**
- Техника создания оптимизированных Docker-образов
- Несколько FROM-инструкций в одном Dockerfile
- Позволяет уменьшить размер финального образа (всё, что не было скопировано из первых слоёв в последний при помощи `COPY --from`, стирается)
- Можно не переносить в верхний слой пакеты, нужные для компиляции других зависимостей (например, `gcc`, `python3-dev`, `libffi-dev` для компиляции `numpy`, `pandas` и т.д.)
```Dockerfile
# Stage 1: Build
FROM python:3.9-slim as builder
WORKDIR /app
COPY requirements.txt . # Install build dependencies and compile packages
RUN apt-get update && apt-get install -y gcc python3-dev \
     && pip install --user -r requirements.txt

# Stage 2: Runtime
FROM python:3.9-slim
# Copy compiled packages
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "app.py"]
```
- Также, если по какой-то причине питонячий сервер раздаёт статику, написанную на каком-то фреймворке, можно в нижних слоях собирать бандл и переносить наверх только его

Пример:
```dockerfile
# Сборочный этап
FROM maven:3.8.1 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn package

# Финальный легковесный образ
FROM openjdk:11-slim
COPY --from=build /app/target/app.jar /app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
```

```bash
docker build -t image-name .
docker run --name container-name image-name
```

Преимущества:
- Уменьшение размера образа
- Исключение инструментов сборки
- Повышение безопасности
- Оптимизация CI/CD процессов

## Сети и тома
**[Сети](https://docs.docker.com/engine/network/)** позволяют контейнерам общаться друг с другом и обращаться к внешним ресурсам. Есть следующие драйверы:
- bridge
     - Используется по умолчанию
     - Позволяет контейнерам в одной сети общаться друг с другом, не позволяет общаться контейнерам из разных сетей
     - Не позволяет общаться контейнерам, относящимся к разным демонам Docker. Для этого есть перекрывающиеся (overlay) сети
     - По умолчанию создаётся сеть данного типа. К ней подключаются все контейнеры, для которых не указана сеть при помощи `--network`. Однако она не позволяет контейнерам обращаться друг к другу по имени - только по IP-адресу. Сети bridge, созданные пользователем, не имеют такого ограничения
- host
     - Убирает сетевую изоляцию между контейнером и хостом
     - Контейнер не получает свой IP-адрес и разделяет *сетевое пространство имён* с хостом (что бы конкретно это ни значило)
     - Проброс портов при помощи `-p`, `--publish` и т.д. не работает и выкидывает предупреждение, потому что если контейнер занимает 80 порт, он будет доступен по адресу хоста на 80 порту
     - Варианты использования:
          - Повышение производительности
          - Контейнеры с огромным количеством торчащих портов
     - Ограничения:
          - Процессы внутри контейнера не могут *привязаться* (bind) к IP-адресу хоста, потому что контейнер не имеет прямого доступа к *интерфейсам* хоста
          - Эта фича в Docker Desktop работает *на 4 уровне*. Это значит, что, в отличие от Docker на Linux, протоколы, находящиеся ниже TCP и UDP по модели OSI, не поддерживаются
          - Эта фича не работает с включённым Enhanced Container Isolation, потому что они противоречат друг другу
          - Эта фича работает только на линуховых контейнерах. Виндовые не поддерживаются. *Не очень-то и хотелось*
- none (изолирует контейнер, контейнеру будет доступен только собственный loopback)
- overlay (позволяет соединять несколько демонов Docker на разных машинах)
- ipvlan (предоставляет полный контроль над IPv4 и IPv6 адресацией)
- macvlan (назначает контейнеру MAC-адрес)

```bash
docker network ls
docker network create mynetwork
docker network inspect

docker network create -d bridge my-net
docker run --network=my-net -itd --name=container3 busybox
```

>[!warning]
>Проброс порта делает его доступным не только хосту, но и всем компьютерам в сети, которые видят хост
>Чтобы сделать порт доступным только хосту и его контейнерам, нужно указать `127.0.0.1` или `::1` при пробросе:
>`docker run -p 127.0.0.1:8080:80 -p '[::1]:8080:80' nginx`

**Тома** - механизм персистентного хранения данных (не удаляется автоматически, содержимое остаётся доступным, даже если ни один контейнер не использует том)
- На хосте хранится в папке
- Управляются докером
- Могут быть именованными и анонимными (докер генерирует уникальное имя, в остальном ведёт себя точно так же, как именовынный том)
- Одинаково работают на виндовых и линуховых контейнерах
- Могут быть разделены между разными контейнерами
- Полезны, когда нужно получать доступ к файлам хоста
- Могут быть объявлены как `read-write` или как `read-only`

## Image
**Image Layer** - промежуточный read-only слой в Docker-образе, создаваемый каждой инструкцией в Dockerfile.

Максимальное количество слоев:
- Docker до версии 1.10: ~42 слоя
- Современные версии: до 127 слоев

Почему важно минимизировать слои:
- Увеличение размера образа
- Замедление сборки
- Увеличение времени загрузки
- Снижение эффективности кэширования

Стратегии оптимизации:
- Объединение связанных команд
- Использование multi-stage build
- Очистка кэша в той же инструкции
- Минимизация количества RUN-инструкций

>[!tip]
>Из-за того, что каждая команда создаёт свой **иммутабельный** слой, удалять ненужные файлы последующими командами бесполезно: "удалённые" файлы не будут доступны в верхних слоях, но всё ещё будут занимать место в предшествующих слою с командой удаления.
>Вместо этого, как указано выше, нужно использовать цепочки команд (через `&&`)

# Kubernetes
## База
**Kubernetes** (K8s) - это платформа для автоматизации развертывания, масштабирования и управления контейнеризированными приложениями.

**Основная идея** Kubernetes заключается в том, чтобы абстрагировать инфраструктуру и предоставить разработчикам единый интерфейс управления приложениями. Вместо ручного управления отдельными серверами и контейнерами Kubernetes позволяет описывать желаемое состояние приложения, после чего самостоятельно поддерживает это состояние.

**Компоненты** Kubernetes можно разделить на две основные группы:
- компоненты управления (**control plane**)
    - **Kube-apiserver** является центральным компонентом, который предоставляет API для взаимодействия с кластером. Через него проходят все запросы на изменение состояния кластера, он валидирует и обрабатывает входящие команды.
    - **Etcd** представляет собой распределённое key-value хранилище, которое служит единственным источником *истины* для состояния кластера. Здесь хранятся все метаданные о конфигурации и текущем состоянии kubernetes-объектов.
    - **Kube-scheduler** отвечает за планирование подов на узлах. Он анализирует требования подов и характеристики узлов, после чего принимает решение о наиболее подходящем узле для запуска.
    - **Kube-controller-manager** - это компонент, который запускает контроллеры, отвечающие за поддержание желаемого состояния кластера. Например, контроллер репликации следит за количеством реплик подов, а контроллер узлов отслеживает состояние worker-узлов.
- рабочие узлы (**worker nodes**)
    - Kubelet - агент, работающий на каждом узле кластера. Он получает инструкции от control plane и следит за состоянием подов, гарантируя их корректную работу.
    - Kube-proxy реализует сетевую логику в кластере, обеспечивая маршрутизацию трафика и настройку правил балансировки нагрузки.

**Структура** Kubernetes основана на иерархии абстракций, которые позволяют гибко описывать и управлять приложениями: на самом низком уровне находятся **контейнеры, которые упакованы в поды** - минимальную единицу развертывания в Kubernetes. **Под** может содержать один или несколько контейнеров, которые совместно используют сетевое пространство и volumes.
**Deployment** представляет собой декларативное описание желаемого состояния подов. Он управляет репликами, обеспечивает обновления и откаты приложений.
**Сервисы** (services) решают задачи сетевого взаимодействия между компонентами. Они абстрагируют поды и предоставляют единую точку входа, что позволяет реализовывать балансировку нагрузки и механизм service discovery.
**Пространства имён** (namespaces) используются для логической изоляции ресурсов внутри кластера, что особенно важно в больших многопользовательских средах.

**Секреты** - это объекты, которые предназначены для безопасного хранения и управления конфиденциальной информацией (пароли, OAuth-токены, SSH-ключи, ...). Принципиальное отличие Секретов от обычных ConfigMap заключается в том, что они хранятся в кластере в зашифрованном виде и имеют дополнительные механизмы защиты.

В Kubernetes существует несколько типов Secrets:
- Docker Registry Secrets - для авторизации в приватных реестрах контейнеров
- TLS Secrets - для хранения сертификатов и приватных ключей
- Basic Authentication Secrets - для хранения credentials
- SSH Secrets - для аутентификации через SSH-ключи

Пример создания Secret:

## Helm, Lens
**[Helm](https://helm.sh/docs/intro/cheatsheet/)** - это пакетный менеджер для Kubernetes, который существенно упрощает процесс установки и управления приложениями. Helm позволяет:
- Описывать комплексные kubernetes-приложения
- Использовать шаблонизацию манифестов
- Управлять зависимостями
- Выполнять откаты и обновления
- Хранить репозитории charts

Helm **Chart** - это пакет, который содержит описание kubernetes-приложения. Он содержит все определения ресурсов, необходимые для запуска приложения, инструмента или сервиса в кубере. Аналог dpkg в Apt или .rmp файла в Yum. Структура включает:

**Lens** - это графический интерфейс управления кластерами Kubernetes. Предоставляет:

- Мониторинг ресурсов
- Интерактивные логи
- Встроенный терминал
- Поддержку множества кластеров

Lens значительно упрощает работу DevOps инженеров, делая взаимодействие с Kubernetes более интуитивным и наглядным.

## Надёжность
Когда происходит сбой узла, Kubernetes автоматически инициирует процесс перемещения pods на другие доступные узлы кластера. Этот механизм базируется на нескольких ключевых компонентах:
- Контроллер репликации (Replication Controller) постоянно мониторит состояние подов и следит за тем, чтобы фактическое количество реплик соответствовало желаемому. Если узел выходит из строя, контроллер немедленно запускает новые поды на альтернативных узлах.
- Механизм самовосстановления (Self-Healing) является фундаментальной особенностью Kubernetes. Система автоматически определяет недоступность узла и перераспределяет нагрузку. Время восстановления обычно составляет от нескольких секунд до нескольких минут, в зависимости от сложности инфраструктуры.

Для повышения отказоустойчивости рекомендуется использовать:
- Стратегию anti-affinity (заставлять scheduler помещать поды в нодах, находящихся далеко друг от друга (настройка зависит от меток (*label*) нод. Например, одну группу подов размещать только в зоне *"antarctica-east-1"*, а другую - где угодно, только не в ней))
- Распределение подов между зонами доступности
- Настройку лимитов ресурсов
- Применение механизмов проб готовности (readiness probe)

Аварийное восстановление ConfigMap предполагает несколько стратегий:
- Резервное копирование через kubectl: `kubectl get configmap -o yaml > configmap-backup.yaml`
- Использование GitOps подходов
- Применение инструментов восстановления типа Velero
- Настройка репликации ConfigMap между кластерами

## Persistent Volume
**Persistent Volume** (PV) и **Persistent Volume Claim** (PVC) - это механизмы управления постоянным хранилищем данных в Kubernetes, который решает критически важную задачу персистентности данных в контейнеризированных средах.

**Persistent Volume** (PV) представляет собой абстракцию физического хранилища данных в кластере Kubernetes. Это независимый от инфраструктуры ресурс, который описывает способ подключения хранилища. PV может быть создан статически (заранее подготовлен администратором) или динамически (автоматически при запросе).

Типы Persistent Volume:
- NFS (Network File System)
- iSCSI
- Cloud Provider volumes (AWS EBS, Azure Disk)
- Local storage
- Distributed storage системы (Ceph, GlusterFS)

Пример описания Persistent Volume:
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  nfs:
    server: nfs-server.default.svc.cluster.local
    path: "/exported/path"
```

**Persistent Volume Claim** (PVC) - это запрос на выделение хранилища со стороны пользователя. PVC описывает требования к объему, способу доступа и характеристикам хранилища. Kubernetes автоматически находит подходящий Persistent Volume и привязывает его к Claims.

Пример Persistent Volume Claim:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```

Механизм работы:
1. Создается Persistent Volume
2. Пользователь создает Persistent Volume Claim
3. Kubernetes находит подходящий PV
4. Происходит привязка PVC к PV
5. Под получает доступ к хранилищу

## [ReplicaSet vs Deployment](https://stackoverflow.com/questions/69448131/kubernetes-whats-the-difference-between-deployment-and-replica-set)
**ReplicaSet** - это низкоуровневый объект, который отвечает за поддержание заданного количества идентичных pods. Основные функции:
- Создание и управление группой реплик
- Обеспечение требуемого количества pods
- Замена упавших или удаленных контейнеров
- Горизонтальное масштабирование

**Deployment** - это более высокоуровневая абстракция, которая предоставляет расширенные возможности управления приложениями. Deployment декларативно описывает желаемое состояние приложения и включает в себя ReplicaSet.

>[!note] Перевод ответа с SO:
>ReplicaSet позволяет установить количество подов в кластере. Поды (также называются репликами) - это механизм обеспечения доступности в кубере. Однако изменение ReplicaSet не влияет на уже созданные поды, поэтому изменить, к примеру, версию образа, не так просто.
>
>Deployment - это более высокий уровень абстракции, управляющий несколькими ReplicaSet и позволяющий осуществлять уонтролируемые обновления. Когда меняется версия образа, создаётся новый ReplicaSet, количество подов в котором постепенно увеличивается с нуля до нужного значения, постепенно заменяя старые поды. Таким образом Deployment реализует rolling update
>
>Вне процесса обновления один Deployment эквивалентен одному ReplicaSet

Ключевые отличия:
- Уровень абстракции
     - ReplicaSet: Низкоуровневое управление репликами
     - Deployment: Высокоуровневое управление жизненным циклом приложения
- Функциональность
     - ReplicaSet: Поддержание количества реплик
     - Deployment: Обновление, откат, паузы, история версий
- Стратегии обновления
     - ReplicaSet: Статичное количество реплик
     - Deployment: Rolling Update, Blue-Green, Canary развертывание
- Управление версиями
     - ReplicaSet: Нет истории версий
     - Deployment: Полная история изменений, возможность отката

Пример Deployment: (за используемый тип отвечает `kind: Deployment`)
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
```

В реальных проектах практически всегда используется Deployment, а не напрямую ReplicaSet, из-за более богатого функционала и удобства управления приложениями.
