## Типы СУБД
1. **Реляционные** базы данных (RDBMS): организуют данные в виде таблиц, связанных между собой. Примеры: MySQL, PostgreSQL, Microsoft SQL Server. Используют SQL (Structured Query Language) для управления данными
2. **Нереляционные** базы данных (NoSQL): не используют таблицы для организации данных. Примеры: MongoDB, Cassandra, Redis.
     1. **Графовые** базы данных: предназначены для хранения и обработки данных в виде графа. Примеры: Neo4j, Amazon Neptune.
     2. **Объектно-ориентированные** базы данных: хранят данные в виде объектов, которые можно использовать напрямую в приложениях. Примеры: Gemstone, Matisse.
     3. **Ключ-значение**: хранят данные в виде пар ключ-значение. Примеры: Valkey, Redis.
     4. **Документо-ориентированные** базы данных: хранят данные в виде документов, таких как JSON, BSON или XML. Примеры: MongoDB, Couchbase.
3. В реляционных применим синтаксис SQL 

## DDL, DML
1. **DDL** – Data Definition Language: `create`, `drop`, `alter`, `truncate`
2. **DQL** – Data Query Language: `select`
3. **DML** – Data Manipulation Language: `insert`, `update`, `delete`, `call`, `explain call`, `lock`
4. **DCL** – Data Control Language: `grant`, `revoke`
5. **TCL** – Transaction Control Language: `commit`, `rollback`, `savepoint`

## Как работает elastic search
1. Использует документно-ориентированную БД и полнотекстовый поиск
2. Поддерживает кластеризацию, репликацию данных и распределённые индексы

## Что за кольцо (токен ринг в cassandra), как работает
1. Виртуальное кольцо, распределяющее данные между нодами кластера
2. Ноды располагаются на этом кольце в зависимости от своего токена. При поступлении новых данных вычисляется хеш первичного ключа и на основе него определяется, какая нода будет хранить эти данные

## Партиционирование и шардирование
1. **Техники для разделения данных и распределения нагрузки на базу данных**
2. **Партиционирование**: это процесс разделения одной таблицы на несколько более мелких таблиц (партиций) для улучшения производительности и масштабируемости. Партиции могут храниться на разных дисках или серверах.
     1. Например, делить таблицу с логами по датам логов (новая таблица на каждый месяц или по диапазону хеша сообщения лога)
     2. `CREATE TABLE logs ... PARTITION BY HASH (message);`
     3. `CREATE TABLE logs_12345 PARTITION OF logs FOR VALUES WITH (modulus 4, remainder 0);`
3. **Шардирование**: это процесс разделения базы данных на несколько более мелких фрагментов (шардов), которые могут храниться на разных серверах. Каждый шард содержит подмножество данных из исходной базы данных.
     1. Например, приложение может выбирать соединение с нужной БД (шардом) по передаваемому ключу данных

## Inverted index
Индекс, который хранит соответствие элементам их положения в таблице (например, в каких строках содержится данная лексема)

## Виды репликации
1. **Мастер-реплика**: один сервер (мастер) принимает все изменения, а остальные серверы (реплики) получают копии изменений от мастера. Мастер может стать узким местом, если он перегружен.
2. **Мульти-мастер**: все серверы могут принимать изменения, а затем синхронизировать данные между собой. Может привести к конфликтам при одновременных изменениях на разных серверах
3. **Синхронная репликация**: изменения синхронизируются между серверами в режиме реального времени. Может замедлить производительность, так как транзакции ждут подтверждения от всех реплик
4. **Асинхронная репликация**: изменения синхронизируются между серверами с задержкой. Может привести к потере данных в случае сбоя мастера
## BASE
1. Противопоставление ACID, когда во главу угла ставится не согласованность, а доступность (например, при добавлении друга в соцсети вообще не важно, что на некоторое время другие пользователи будут видеть неправильное количество друзей у тебя. Главное, чтобы доступ к БД не прерывался на время добавления друга и всем можно было продолжать листать ленту)
     1. **Basically available**: база данных должна быть доступна одновременно для всех пользователей в любое время. Пользователю не нужно ждать, пока завершатся другие транзакции, прежде чем обновлять запись
     2. **Soft state**: любые данные могут находиться в промежуточных или временных состояниях и в некоторый момент изменяться «сами по себе», без внешних событий или поступления новых данных. Эта концепция отражает неопределенное состояние записи, которую обновляют несколько приложений одновременно. Значение такой записи будет окончательно определено только после завершения всех транзакций
     3. **Eventually consistent**: запись достигнет согласованности не сразу, а после завершения всех одновременных обновлений. После этого все приложения, запрашивающие эту запись, увидят одно и то же значение
## ACID
1. **ACID** (Atomicity, Consistency, Isolation, Durability) - это **набор свойств транзакций**, которые обеспечивают надежность транзакций и обеспечивают целостность данных при параллельной работе и сбоях в базах данных.
     1. *Нужна для проведения миграций в БД*
2. **Атомарность** (Atomicity): каждая транзакция должна быть выполнена полностью или не выполнена вообще.
3. **Согласованность** (Consistency): данные должны оставаться в согласованном состоянии **относительно бизнес-логики** после выполнения транзакции. Гарантирует соответствие данных заранее заданным ограничениям по целостности и бизнес-правилам
4. **Изоляция** (Isolation): гарантирует, что каждая новая транзакция, обращающаяся к определенной записи, должна до начала работы дождаться завершения предыдущей транзакции. Это гарантирует, что параллельные транзакции не будут мешать друг другу, как если бы они выполнялись последовательно
5. **Стойкость** (Durability): сохранение всех зафиксированных транзакций в базе данных даже в случае сбоя системы
## CAP
1. **CAP** - это теорема, которая описывает trade-off между согласованностью, доступностью и устойчивостью к разделению в распределенных системах.
     1. **Consistency** (согласованность): каждый запрос на чтение возвращает последнюю записанную версию или ошибку, если согласованность не может быть гарантирована
     2. **Availability** (доступность): запросы не возвращают ошибку даже в случае, если ноды недоступны
     3. **Partition tolerance** (устойчивость к разделению): система продолжает работу даже в случае потери произвольного количества сообщений между нодами (*Максим говорит, что это больше про намеренное разделение, например, разные таблицы на разных хостах*)
2. Необходима для понимания ограничений распределенных систем и выбора правильного баланса между согласованностью, доступностью и устойчивостью к разделению
3. **Одновременно** могут быть гарантированы не ровно два из трёх, а не больше двух
4. ==по умолчанию в постгре - CA==
     1. посмотреть в одиночном (CA), с репликацией (CA/CP), с кластеризацией (CA/CP)

## PACELC [xd](https://habr.com/ru/companies/gaz-is/articles/551986/)
1. **PACELC** - это расширение теоремы **CAP**, которое добавляет параметр **Задержка** (Latency). Описывается так: `if P, then A or C, else L or C`
2. В случае разделения сети в распределённой компьютерной системе необходимо выбирать между доступностью и согласованностью, но даже если система работает нормально при отсутствии разделения, нужно выбирать между задержками и согласованностью
3. Как и в CAP, есть разные конфигурации СУБД:
     1. **PA/EL**: высокая доступность \(A\) при разделении \(P\) системы иначе \(E\) высокая скорость ответа \(L\)
     2. **PC/EC**: жертвовать доступностью \(A\) в угоду консистентности \(С\), используя огораживание (fencing) при разделении \(P\) в распределённых системах. В неразделённых \(E\)lse системах «под нож» пойдёт скорость \(L\)atency, так как консистентность – это один из столпов ACID
     3. **PC/EL**: Данная архитектура при разделении стремится оставаться консистентной, а в случае без сетевых разделений, фокусируется на скорости ответа, отводя консистентность на второй план
     4. **PA/EC**: При наличии сетевого разделения системы ставка делается на доступность, а при отсутствии распределения – на консистентность

## INSERT INTO SELECT
1. Оператор `INSERT INTO SELECT` позволяет вставлять данные из одной таблицы в другую таблицу.
     1. также может использоваться для вставки данных в существующие строки, если это необходимо
2. Состоит из двух частей: `INSERT INTO`, которая указывает таблицу, в которую будут вставлены данные, и `SELECT`, которая указывает таблицу, из которой будут взяты данные.
     1. `SELECT` может включать условия, чтобы ограничить количество вставляемых данных
3. Позволяет копировать данные из одной таблицы в другую, а также позволяет преобразовывать данные во время копирования
     1. преобразование данных может включать использование функций и выражений
## UNION
1. Оператор `UNION` позволяет объединить результаты двух или более запросов `SELECT` в один результат.
     1. все объединяемые запросы должны иметь одинаковое количество столбцов и совместимые типы данных
2. Удаляет дубликаты строк из результата.
     1. для сохранения дубликатов можно использовать оператор `UNION ALL`
3. Можно использовать для объединения данных из разных таблиц или для объединения данных из одной таблицы, но с разными условиями
     1. `UNION` может использоваться для объединения данных из разных таблиц с одинаковой структурой
4. `SELECT * FROM таблица1 UNION SELECT * FROM таблица2;`

## Кластеризованные и некластеризованные индексы
1. **Кластеризованный индекс**: индекс, который хранит данные в том же порядке, в котором они хранятся в таблице. В таблице может быть только один кластеризованный индекс, так как он определяет физический порядок строк
2. **Некластеризованный индекс**: индекс, который хранит данные в отдельном от таблицы месте. Содержит указатели на строки в таблице, что может замедлить доступ к данным
3. Кластеризованный индекс быстрее, чем некластеризованный, но он требует больше места на диске. Также кластеризованный индекс может быть медленнее при вставке и обновлении данных, так как требуется поддерживать физический порядок
4. Какие структуры данных используются в обоих видах
     1. Для кластеризованных - древовидные структуры, листья содержат ссылки на соседей
     2. Для некластеризованных - древовидные плюс хеш-таблицы и битовые карты
5. **Сферическое объяснение в вакууме**: кластеризованный содержит сами значения, некластеризованный - ссылки на строки

## Primary key и Foreign key
1. **Primary key**: первичный ключ - это уникальный идентификатор строки данных в таблице. Первичный ключ не может быть `NULL` и не может дублироваться.
2. **Foreign key**: внешний ключ - это поле в таблице, которое ссылается на первичный ключ другой таблицы. Внешний ключ используется для создания связей между таблицами
     1. внешний ключ может иметь ограничения, такие как каскадное обновление или удаление

## Уровни изоляции, аномалии
1. Уровни изоляции
     1. **READ UNCOMMITTED**: позволяет читать незафиксированные данные.
     2. **READ COMMITTED**: позволяет читать только зафиксированные данные, но не защищает от неповторяющегося и фантомного чтения. (по умолчанию в Postgres)
     3. **REPEATABLE READ**: позволяет читать данные, которые были зафиксированы до начала транзакции, но не защищает от фантомного чтения (чтение строк по одинаковому условию два раза, между которыми другая транзакция добавляет новые строки, удовлетворяющие этому условию). (по умолчанию в MySQL)
          1. транзакция видит данные, которые были зафиксированы до ее начала, и не видит изменений, сделанных другими транзакциями
     4. **SERIALIZABLE**: позволяет читать данные, которые были зафиксированы до начала транзакции, и блокирует запись данных, которые были изменены другими транзакциями
          1. обеспечивает наивысший уровень изоляции и предотвращает все виды аномалий
          2. заставляет транзакции выполняться последовательно
2. **Аномалии**:
     1. **Dirty read**: чтение незафиксированных данных.![image](Static/4.anomalies-dirty-read.png)
     2. **Non-repeatable read**: чтение данных, которые были изменены другими транзакциями. ![image](4.anomalies-non-repeatable-read.png)
     3. **Phantom read**: чтение данных, которые были добавлены другими транзакциями.![image](4.anomalies-phantom-read.png)
     4. **Lost update**: потеря изменений, внесенных одной транзакцией, из-за изменения данных другой транзакцией ![image](4.anomalies-lost-update.png)
     5. **Deadlock**: когда две или более транзакций блокируют друг друга, ожидая доступа к ресурсам, которые уже заняты другой транзакцией.
     6. **Starvation**: когда одна транзакция не может получить доступ к ресурсам, которые необходимы ей для выполнения, из-за других транзакций, которые удерживают эти ресурсы.
     7. **Livelock**: когда две или более транзакций постоянно переключаются между собой, пытаясь получить доступ к ресурсам, которые уже заняты другой транзакцией.

## CQRS
1. **CQRS** (Command Query Responsibility Segregation) - это архитектурный паттерн, который разделяет ответственность за обработку команд и запросов.
2. Необходим для разделения сложных систем на более простые и независимые компоненты.
3. Реализуется с помощью команд и запросов, которые обрабатываются отдельными компонентами системы
     1. Есть отдельная БД на чтение, есть отдельная БД на запись (пишутся команды на изменение состояния, эта БД представляет собой очередь)
     2. Специальные обработчики берут команды из второй БД и в соответствии с ними изменяют первую
4. ==Две реализации:==
     1. расшиненная (две бд)
     2. упрощённая (всё записываются в одну таблицу, разделяются только команды)

## Триггеры
1. специальные процедуры, которые автоматически выполняются при определенных событиях в базе данных, таких как добавление, удаление или изменение данных. Триггеры можно использовать для обеспечения целостности данных, выполнения бизнес-логики и автоматизации процессов.
2. Триггеры можно разделить на следующие типы:
     1. **Before триггеры**: выполняются перед выполнением операции над данными. 
     2. **After триггеры**: выполняются после выполнения операции над данными.
     3. **Instead of триггеры**: выполняются вместо операции над данными.
3. Триггеры можно использовать для следующих целей:
     1. **Проверка данных**: триггеры можно использовать для проверки данных на соответствие определенным правилам или условиям.
     2. **Автоматизация процессов**: триггеры можно использовать для автоматизации процессов, таких как отправка уведомлений или обновление данных.
     3. **Обеспечение целостности данных**: триггеры можно использовать для обеспечения целостности данных, таких как проверка уникальности данных или обеспечение соответствия данных определенным правилам.
     4. **Выполнение бизнес-логики**: триггеры можно использовать для выполнения бизнес-логики, такой как расчеты или проверки
## Нормальные формы баз данных
1. **Нулевая**: до нормализации
     1. Несколько значений в одном столбце ![image](Static/4.nf-0.png)
     2. Аномалии, воникающие в данной ненормализованной БД:
          1. **Аномалия вставки**. При добавлении нового «Сотрудника» (**employee**) в «Отдел» (**sector**) _Finance_, обязательно указывается его «Руководитель» (**manager**). Иначе вы не сможете вставить данные в таблицу.
          2. **Аномалия обновления.** Когда сотрудник переходит в другой отдел, поле «Руководитель» содержит ошибочные данные. К примеру, _Jacob_ перешел в отдел _Finance_, но его руководителем по-прежнему показывается _Adam_.
          3. **Аномалия удаления**. Если _Joshua_ решит уволиться из компании, то при удалении строки с его записью потеряется информация о том, что отдел _Finance_ вообще существует.
2. **Первая**: Каждая ячейка таблицы должна содержать **только одно значение**.
     1. Разбиваются повторяющиеся и сложные значения; все экземпляры становятся атомарными
     2. Нет зависимости от первичного ключа ![image](Static/4.nf-1.png)
3. **Вторая**: Каждое поле таблицы должно **зависеть от всего первичного ключа**. Это означает, что если таблица имеет составной первичный ключ, то каждое поле должно зависеть от всех частей ключа.
     1. Частичные зависимости разделяются на новые таблицы. Все строки функционально зависимы от первичного ключа
     2. Разбивается на две таблицы: менеджеров и сотрудников ![image](Static/4.nf-2-1.png)
     3. Всё ещё присутствует зависимость сотрудника от сектора ![image](Static/4.nf-2-2.png)
4. **Третья**: Если таблица находится во второй нормальной форме, то каждое поле, которое не является частью первичного ключа, **должно зависеть только от первичного ключа**. Это означает, что если поле зависит от другого поля, которое не является частью первичного ключа, то оно должно быть перемещено в другую таблицу
     1. Транзитивные зависимости разбиваются на новые таблицы. Не ключевые атрибуты зависят от первичного ключа
     2. Сектор выносится в отдельную таблицу ![image](Static/4.nf-3-1.png)
     3. Теперь все транзитивные зависимости вынесены в отдельные таблицы ![image](Static/4.nf-3-2.png)
5. **Нормальная форма Бойса-Кода (BCNF)**: Транзитивные и частичные функциональные зависимости для всех потенциальных ключей разбиваются на новые таблицы
     1. Является более строгой версией 3НФ

## View
Это виртуальная таблица, которая основана на одной или нескольких таблицах базы данных. View не хранит данные самостоятельно, а вместо этого предоставляет доступ к данным из других таблиц. Можно использовать для упрощения доступа к данным, для обеспечения безопасности и для предоставления дополнительной функциональности

## Heterogeneous calls
1. Heterogeneous calls - это вызовы функций или процедур, которые выполняются в разных базах данных или системах.
2. Используются для обеспечения взаимодействия между различными системами и базами данных.
3. Могут быть использованы для выполнения запросов, обновления данных и вызова функций в разных системах

## Пакет в БД
Набор процедур, функций и переменных, которые объединены в одну единицу. Можно использовать для упрощения доступа к данным и функциям, а также для обеспечения безопасности и контроля доступа. Можно использовать в различных базах данных, включая Oracle, MySQL и PostgreSQL

## Virtual Table
Виртуальная таблица, которая основана на одной или нескольких таблицах базы данных. Не хранит данные самостоятельно, а вместо этого предоставляет доступ к данным из других таблиц. Можно использовать для упрощения доступа к данным, для обеспечения безопасности и для предоставления дополнительной функциональности

## Конструкция WITH ... AS
1. синтаксис, который позволяет создавать временные (виртуальные) таблицы или представления в базе данных. Эта конструкция называется **CTE** (Common table expression)
2. `WITH клиенты_россии AS ( SELECT * FROM клиенты WHERE страна = 'Россия' ) SELECT * FROM клиенты_россии;`

## Оконные функции
1. Оконные функции - это тип функций, которые позволяют выполнять операции над данными в таблице, используя окно, которое перемещается по строкам таблицы. Оконные функции можно использовать для выполнения различных задач, таких как:
     1. Вычисление среднего значения или суммы данных в окне
     2. Вычисление ранга или процентила данных в окне
     3. Вычисление лага или опережения данных в окне
2. Примеры оконных функций:
     1. `ROW_NUMBER()`
     2. `RANK()`
     3. `DENSE_RANK()`
     4. `PERCENT_RANK()`
     5. `CUME_DIST()`
     6. `LAG()`
     7. `LEAD()`
3. Применение оконных функций:
     1. Анализ данных по времени
     2. Анализ данных по группам
     3. Вычисление статистических показателей
     4. Создание отчетов и графиков
4. **Скользящее среднее** - тип оконной функции, которая вычисляет *среднее значение данных в окне, которое перемещается по строкам таблицы
     2. `SELECT AVG(значение) OVER (ORDER BY дата ROWS 10 PRECEDING) AS скользящее_среднее FROM таблица;`
5. ==Виды==
     1. ранжирование (ранги окна, по ключу взяли, когда нужно избавиться от дубликатов и сделать операцию срочно)
     2. суммирование (сумма окна)
     3. скользящее среднее

## Соединения (JOIN)
1. Есть два типа:
     1. `INNER` возвращает строки, у которых есть соответствующие значения в обеих таблицах
     2. `OUTER` возвращает все строки, даже те, для которых совпадение не найдено
          1. Делится на `LEFT`, `RIGHT` и `FULL` (Если для какой-либо из таблиц не нашлось строки в другой таблице, то строка все равно попадает в результат, а значения столбцов другой таблицы равны `NULL`)
          2. `CROSS` - декартово произведение (все строки со всеми). Синтаксис `FROM table1 CROSS JOIN table2` или `FROM table1, table2`
2. Различия между LEFT и RIGHT JOIN
     1. `LEFT JOIN` - это тип соединения, который возвращает все строки из левой таблицы и соответствующие строки из правой таблицы. Если нет соответствующих строк в правой таблице, то возвращаются `NULL`-значения.
     2. `RIGHT JOIN` - это тип соединения, который возвращает все строки из правой таблицы и соответствующие строки из левой таблицы. Если нет соответствующих строк в левой таблице, то возвращаются `NULL`-значения
3. Self-join
     1. тип соединения таблицы с самой собой
     2. Можно использовать для
          1. Вычисления рекурсивных отношений
          2. Вычисления иерархических отношений
          3. Создания отчетов и графиков

## Ограничения целостности
1. `PRIMARY KEY`: определяет уникальный идентификатор для каждой строки таблицы.
2. `UNIQUE`: гарантирует, что значения в столбце или группе столбцов уникальны.
3. `FOREIGN KEY`: ссылается на `PRIMARY KEY` другой таблицы, чтобы установить связь между таблицами.
4. `NOT NULL`: требует, чтобы столбец имел значение, т.е. не может быть `NULL`.
5. `CHECK`: проверяет, что значения в столбце удовлетворяют определённому условию.
6. `DEFAULT`: устанавливает значение по умолчанию для столбца, если значение не указано.

## Различия Primary key и UNIQUE
`PRIMARY KEY` и `UNIQUE` — оба обеспечивают уникальность значений в столбце или группе столбцов. Однако `PRIMARY KEY` не может быть `NULL`, в то время как `UNIQUE` может быть `NULL`. Кроме того, в таблице может быть только один `PRIMARY KEY`, но может быть несколько `UNIQUE` ключей

## Для чего нужно геолокационное шардирование?
Для разделения данных по географическому принципу. Например, если у вас есть база данных с информацией о пользователях из разных стран, вы можете разделить данные на шарды по странам. Это может уменьшить нагрузку на сервер и улучшить производительность запросов

## Назначение оператора `RETURNING`
Используется в SQL-запросах для возврата значений, которые были изменены или удалены. Например, если вы хотите вернуть идентификатор записи, которую вы только что добавили, вы можете использовать конструкцию `RETURNING` в запросе `INSERT`

## Какой код выполняется быстрее: в БД или на бэкенде?
На БД. База данных оптимизирована для работы с данными и имеет специальные алгоритмы и структуры данных для ускорения запросов. А ещё её процедуры компилируются

## Использование Redis в качестве брокера сообщений
1. Redis может быть использован как брокер сообщений, позволяя приложениям отправлять и получать сообщения друг другу. Это может быть полезно для реализации архитектуры микросервисов, где несколько приложений могут общаться друг с другом.
2. В Redis можно использовать следующие команды для работы с брокером:
          1. `PUBLISH`: отправляет сообщение в канал.
          2. `SUBSCRIBE`: подписывается на канал и начинает получать сообщения.
          3. `UNSUBSCRIBE`: отменяет подписку на канал

## База не тянет текущие объемы. Что делать?
- Увеличить количество процессоров, оперативной памяти или дискового пространства на сервере, где находится база данных.
- Проанализировать запросы, которые выполняются в базе данных, и оптимизировать их для уменьшения нагрузки.
     - убрать ненужные столбцы
     - посмотреть, подходит текущий ли тип индекса
     - проверить селективность индекса
     - *хранить хеши вместо значений*
- Добавить индексы к столбцам, которые часто используются в запросах, для ускорения поиска данных.
- Разделить базу данных на несколько фрагментов (шардов) и распределить их между несколькими серверами.
- Создать копию базы данных на другом сервере и использовать ее для чтения данных, чтобы уменьшить нагрузку на основную базу данных

## Репликация
1. **Репликация** - это создание копий базы данных для обеспечения доступности и надёжности хранения данных. Репликация может быть использована для распределения нагрузки и защиты данных от потери, а также для резервного копирования и восстановления данных, в том числе для геораспределенных систем
2. В postgres:
     1. **Shared Dick Failover** - несколько серверов СУБД имеют доступ к одному набору физических дисков. Если один сервер падает, то другой сервер может подключиться к этим дискам и заменить собой упавший сервер
     2. **File System** - имеется минимум один дополнительный хост, на который пишутся данные в том же порядке, что и в текущую файловую систему
     3. **WAL Shipping** - на удалённый сервер пишутся все записи из WAL, что позволяет сохранить почти все данные в случае падения основного сервера
     4. **Логическая репликация** - сервер СУБД отправляет поток изменений данных на удалённый сервер. Также сервер может параллельно принимать поток изменений от третьего сервера
     5. **Репликация на основе триггеров** обычно направляет запросы модификации данных на выделенный главный сервер. Работая на уровне отдельных таблиц, главный сервер отправляет изменения данных (как правило) асинхронно на резервные серверы. Резервные серверы могут обрабатывать запросы во время работы первичного сервера и могут допускать некоторые локальные изменения данных или операции записи. Такая форма репликации часто используется для выгрузки больших аналитических запросов или запросов к хранилищам данных
     6. **SQL-Based Replication Middleware** - есть перехватчик всех SQL запросов, который отправляет их одному или нескольким удалённым серверам. Запросы чтения-записи обязаны отправляться всем серверам, а запросы только на чтение могут отправляться только одному серверу для балансировки нагрузки
     7. **Asynchronous Multimaster Replication** - все сервера работают независимо и время от времени синхронизируются для решения конфликтов (конфликты решаются в соответствии с установленными правилами или вручную)
     8. **Synchronous Multimaster Replication** - запросы на запись сначала передаются всем остальным серверам перед тем, как транзакция будет зафиксирована, что ведёт к большим накладным расходам и трате времени. Запросы на запись могут быть отправлены на любой сервер
     9. [Весёлая таблица с доки](Additional_notes/4.Postgres_replication_table.md)
3. **Виды репликации по Толе**:
     1. физическая
     2. локальная
     3. синхронная\асинхронная (в синхронной есть блокировка, в асинхронной - нет)
     4. симметрическая (не является обязательной)

## MVCC
1. **MVCC** (Multi-Version Concurrency Control) - это механизм управления конкурентным доступом к данным в базах данных.
2. На смену блокировочному протоколу (потому что он очень медленный) пришёл протокол изоляции на основе снимков (*Snapshot Isolation, SI*). Его идея состоит в том, что каждая транзакция работает со своим согласованным снимком данных на определённый момент времени
3. Позволяет обходиться минимумом блокировок: фактически блокируется только изменение одной и той же строки. Пишущие транзакции не блокируют читающие, а читающие не блокируют никого
4. В PostgreSQL реализован многоверсионный вариант протокола: в один момент времени может существовать несколько версий одной строки
5. По определению не допускается грязное чтение. Указать Read Uncommitted можно, но работать он будет точно так же, как Read Committed
6. Repeatable Read в данной реализации не допускает фантомное чтение
7. Страница, хранящая строки таблицы, хранит все версии строк
     1. `xmin`, `xmax` - отличают данную версию от других версий той же строки)
          1. **xid**: идентификатор транзакции (transaction ID). Каждой транзакции присваивается уникальный `xid`.
          2. **xmin**: идентификатор начальной транзакции (`xmin`) - это `xid` транзакции, которая создала строку данных. `xmin` также используется для определения, какие транзакции могут видеть данную строку
          3. **xmax**: идентификатор конечной транзакции (`xmax`) - это `xid` транзакции, которая удалила строку данных. Если строка не удалена и является актуальной, `xmax` равен 0
     2. `UPDATE` может рассматриваться как `DELETE` + `INSERT`: текущей версии строки устанавливается значение `xmax` = `xid` транзакции, выполнившей `UPDATE`, а затем создаётся новая версия строки с `xmin` = `xid` той же транзакции
     3. `infomask` - информационные биты, определяющие свойства версии
     4. `ctid` - ссылка на более новую версию строки
     5. `cmin`, `cmax` - порядковый номер операции внутри транзакции (нужно при определении, видна ли версия строки изнутри транзакции, которой она принадлежит: например, курсор не может видеть изменения, сделанные после его открытия). Отображают номер операции вставки и номер операции удаления соответственно
     6. битовая карта неопределённых значений - биты, определяющие, какие столбцы допускают `NULL`

### Горизонт транзакции
1. **Горизонт транзакции** - нижняя граница снимка (номер `xmin` самой ранней транзакции, активной на момент его создания)
2. Все транзакции, находящиеся под горизонтом (`xid` < `xmin`) уже гарантированно зафиксированы. Следовательно, за своим горизонтом транзакция видит только актуальные версии строк

## В основные различия между VACUUM и VACUUM FULL? И какие блокировка накладывают?
1. `VACUUM`: команда `VACUUM` удаляет уже не нужные версии строк из таблицы и ссылки на них из всех индексов. Также решает проблему переполнения 32-битного счётчика транзакций, помечая слишком старые транзакции как "замороженные", что позволяет изменениям, сделанным ими, быть видными из любых транзакций без оглядки на `xmin`
2. `VACUUM FULL`: команда `VACUUM FULL` также удаляет мертвые строки данных, но кроме того, она еще и переставляет живые строки данных в начале таблицы, что может уменьшить размер таблицы. Также перестраивает индексы
3. **Блокировки**: `VACUUM` накладывает `SHARE UPDATE EXCLUSIVE` блокировку на таблицу, что позволяет другим транзакциям читать таблицу, но не позволяет выполнять операции записи. `VACUUM FULL` накладывает `ACCESS EXCLUSIVE` блокировку на таблицу, что запрещает любые операции чтения или записи
     1. `VACUUM` может накладывать блокировки на уровне строк, в то время как `VACUUM FULL` требует блокировки на уровне таблицы (и чтение, и запись)

## Реализация полнотекстового поиска в PostgreSQL
**Важно**: отвечать на этот вопрос кратко. *Не растекаться мыслью по древу относительно реализации джина и гиста, сам закопаешься и собеседующего задушишь*
>[!tip] Например, так:
>Текст разбивается на лексемы, и поиск производится по ним. 
>Есть индекс GIN (плюс RUM) для статических данных и чтения, есть индекс GIST для динамических данных и записи 
>(потому что перестраивать джин дольше, чем гист, но работает джин быстрее, потому что специализированный)

Гопота
- Полнотекстовый поиск в PostgreSQL реализован с помощью модуля `pg_trgm` (trigram) и модуля `pg_ts` (text search).
- `pg_trgm` позволяет создавать триграммы (последовательности из трех символов) из текстовых данных, что позволяет эффективно искать строки данных по подстрокам.
     - `pg_trgm` используется для триграммного поиска, который не является полнотекстовым поиском в строгом смысле
- `pg_ts` позволяет создавать текстовые индексы, которые могут быть использованы для полнотекстового поиска
     - `pg_ts` включает в себя такие компоненты, как токенизация, стемминг и создание индексов

Книга
- Для применения полнотекстового поиска документ приводится к специальному типу `tsvector`, который содержит лексемы (слова, приведённые к виду, удобному для поиска: отбрасываются окончания, приводятся к нижнему регистру, стоп-слова (слишком короткие и часто используемые слова) игнорируются) и их позиции в документе
- Запрос (представленный типом `tsquery`) состоит из одной или нескольких лексем, соединённых логическими связками: "и", "или", "не" и скобками для уточнения приоритета операций
- Текст не обязан храниться в одном столбце: можно выполнять поиск и индексирование и по, например, конкатенации нескольких столбцов
- Для индексации GiSTом используются не сами лексемы, а их сигнатуры
     - Сигнатура лексемы - битовая строка из всех нулей и одной единицы, чья позиция в строке определяется при помощи хеш-функции от лексемы. Это нужно, чтобы не хранить все лексемы в узлах дерева, что раздувало бы его размер (а то и вообще делало невозможным умещение одного узла в одну страницу)
     - Сигнатура документа - битовое ИЛИ сигнатур всех лексем документа
     - Это позволяет сильно уменьшить размер индекса, но влечёт следующие проблемы:
          - Ложноположительные срабатывания за счёт использования хеш-функции
          - Нельзя ограничиться сканированием только индекса, потому что индекс не хранит значения ключей индексирования, и нужно перепроверять по таблице

## Разница между DELETE и TRUNCATE (DROP туда же)
1. Оператор `DELETE` удаляет строки данных из таблицы, но не меняет структуру таблицы.
2. Оператор `TRUNCATE` опустошает таблицу (нельзя указать условие, по которому нужно удалять строки, он чистит всё)
     1. Не только сбрасывает идентификаторы строк, но и не вызывает `ON DELETE` триггеры. Вызывает `ON TRUNCATE` триггеры. Также `TRUNCATE` не обновляет статистику таблицы, как это делает `DELETE`
     2. Может перезапускать последовательности (для идентификаторов, например). Для этого нужно указать `RESTART IDENTITY`
     3. Очищает место на диске немедленно, не требует `VACUUM`. Больше походит для больших таблиц, чем `DELETE`
     4. Не MVCC-friendly: параллельные транзакции после очистки будут видеть таблицу пустой
     5. Обратим: если транзакция не будет зафиксирована, удаления строк не произойдёт
     6. `TRUNCATE` не может быть использован, если на таблице есть внешние ключи, ссылающиеся на нее, без предварительного удаления этих ссылок
     7. Захватывает эксклюзивную блокировку на все очищаемые таблицы
3. `DELETE FROM таблица WHERE условие;`
4. `TRUNCATE TABLE таблица;`

## Индексы
1. **Индекс** - объект БД, предназначенный для ускорения доступа к данным
2. актуальность индекса: Рома уверен, что индексы обновляются сами, и, похоже, он [прав](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/indexes-and-index-organized-tables.html#GUID-A444A178-67BE-45E2-8D2F-A64B95E1D31F)
          1. *The database must update the index when DML occurs on the indexed data, which creates performance overhead.*
2. методы доступа (==Рома уверен, что это просто второе название индексов, в книге написано по-другому==)
3. **B-tree индекс**: индекс, который хранит данные в виде дерева, где каждый узел содержит ключ и указатель на следующий узел. Является стандартным типом индекса в PostgreSQL и используется по умолчанию. Не приспособлен для возврата нескольких значений - должен вернуть только одно
4. **Hash индекс**: индекс, который хранит данные в виде хеш-таблицы, где каждый ключ соответствует значению. Поддерживает только поиск по условию равенства. Допускает ложноположительные срабатывания, поэтому проверяет все возвращённые строки на удовлетворение условию
     1. Почему он считается тяжёлым
          1. Полное перестроение индекса при изменениях
          2. Высокая нагрузка на процессор при хешировании
          3. Необходимость полного сканирования при обновлениях
5. **Bloom**
     1. Использует фильтры Блума - вероятностную структуру данных, применяемую для определения, входит ли элемент в множество или нет, при помощи хеш-функций. Возможны ложноположительные срабатывания
          1. ![image](Static/4.bloom-1.png)
          2. Есть битовая последовательность размером $m$, по которой будет проверяться факт вхождения элемента в множество
          3. Также есть набор из $k$ независимых хеш-функций, которые будут определять позиции единиц в битовой последовательности
          4. Элемент входит во множество, если для каждого индекса, возвращённого хеш-функциями, в битовой последовательности под данным индексом находится единица
     2. Предназначен для быстрого отсечения неподходящих строк
     3. Поддерживает только проверку равенства (в отличие от B-tree, который поддерживает также проверки неравенства и вхождения в диапазон)
     4. **Важное** свойство - может возвращать несколько строк (*что в принципе логично, просто это нужно отдельно проговаривать*)
6. **GIN индекс** (Generalized Inverted Index)
     1. гопота: индекс, который хранит данные в виде инвертированного индекса, где каждый ключ соответствует списку значений. Особенно полезны для полнотекстового поиска и работы с массивами
          1. **элемент** - значение, которое мы индексируем (например, текст)
          2. **ключ** - *element value* (вроде обозначает значение, по которому мы будем искать)
          3. индекс такого типа хранит набор пар (ключ, список идентификаторов строк, значения которых включают данный ключ)
               1. один идентификатор строки может встречаться несколько раз в разных парах, потому что значение может содержать несколько ключей
     2. книга
          1. Данный индекс работает с типами данных, значения которых состоят из элементов и индексирует именно элементы. Хорошая аналогия - предметный указатель в конце книги. По одному элементу можно перейти во все стоки, содержащие данный элемент
          2. Полагается на то, что элементы составных значений можно упорядочить, и в качестве основной структуры данных использует B-дерево
          3. Основная область применения - полнотекстовый поиск, но может применяться и для целочисленных массивов, и для JSON
          4. Из-за того, что документы содержат много лексем, подлежащих индексированию, при изменении даже одного документа нужно вносить множество изменений в дерево индекса, и индекс обновляется медленно
7. **GiST индекс** (Generalized Search Tree): индекс, который хранит данные в виде дерева.
     1. В отличие от сбалансированного дерева не привязан к порядковым типам. Может возвращать несколько значений
     2. Позволяет определять собственные операторы для новых типов данных при помощи определения опорных функций
          1. Функция согласованности определяет, согласовывается ли предикат данной записи с условием поиска (если узел внутренний - нужно ли спускаться в соответствующее поддерево; если узел листовой - удовлетворяет ли условие ключу индексирования)
          2. Штрафная функция используется для определения узла с минимальной стоимостью вставки при вставке нового значения в дерево
     3. Добавление новых значений ведёт к расщеплению предикатов, а сужение - только при перестройке и расщеплении страницы, что ведёт к деградации производительности индекса при частых обновлениях
     4. Листы содержат предикат (логическое условие) и идентификатор табличной версии строки
     5. Внутренние узлы содержат предикат и ссылку на дочерний узел. Предикат внутренней записи включает в себя предикаты всех дочерних записей
     6. Использует поиск в глубину, чтобы начать возвращать строки как можно быстрее
     7. Может применяться для геометрических, диапазонных, порядковых типов, сетевых адресов, целочисленных массивов, триграмм и прочего
8. **SP-GiST индекс** (Space Partitioning GiST)
     1. Под пространством понимается произвольная область значений. Идея состоит в рекурсивном разбиении пространства на непересекающиеся области. Это образует несбалансированные деревья, обычно большой глубины. В свою очередь это порождает проблему эффективной упаковки узлов в страницы для минимизации операций ввода-вывода
     2. Внутренний узел содержит значение, соответствующее условию, которое выполняется для всех дочерних узлов (префикс). Он играет ту же роль, что и предикат в GiST. Ссылки на дочерние узлы могут иметь метки
     3. Листья содержат индексируемое значение (или его часть) и идентификатор соответствующей версии строки
     4. Может использоваться для геометрических и диапазонных типов и сетевых адресов
     5. Опорные функции
          1. Функция согласованности похожа на аналогичную из GiST. Она используется для определения, в какие поддеревья заходить, для внутреннего узла (функция выбирает узлы, не спускаясь в них, а ориентируясь на значения префикса и меток), и удовлетворяет ли значение поисковому предикату для листа
          2. Для вставки используется функция выбора (определяет, в какой узел отправлять новую запись) и функция расщепления (при переполнении страницы решает, какие узлы переносить на новую страницу)
     6. Пример для точек (дерево квадрантов):
          1. Область рекурсивно разбивается на четыре области (квадранта) по отношению к выбранной точке, которая называется центроидом и служите префиксом узла (условием, определяющим положение дочерних значений). Разбиение повторяется, пока не будет получено итоговое разбиение. Точки, лежащие чётко на границах, относятся к квадранту с меньшим номером
          2. ![image](Static/4.sp-gist-1.png)
          3. ![image](Static/4.sp-gist-2.png)
     7. Также можно использовать k-мерные деревья (каждое пространство делится не на 4 части, а на k. Например, при k=2 каждое пространство делится напополам)
     8. Также можно использовать префиксное дерево для строк, в котором префикс - это именно префикс всех дочерних строк, а ссылки на дочерние узлы помечены первым байтом значений, идущих за префиксом
     9. [file](/Checks/Additional_notes/4.Database_Indexes.md)
9. **BRIN индекс** (Block Range Index): предназначен для отсечения заведомо не нужных строк в огромных таблицах (десятки терабайт). В силу этого не хранит идентификаторы версий строк - только некоторую сводную информацию по зонам (единицы разбиения таблиц, занимающие по несколько страниц)
     1. При запросе отсекаются зоны, значения в которых гарантированно не попадают под условие запроса. Все строки из возвращённых индексом зон проверяются на соответствие условию (индекс возвращает неточную битовую карту зон)
     2. Хорошо работает для столбцов, значения в которых локализованы (значения рядом друг с другом имеют сходные свойства (например, целые числа отсортированы))
10. **RUM**
     1. Расширение индекса GIN, решающее следующие проблемы:
          1. **Медленное ранжирование** из-за того, что GIN не хранит позиции лексем в строках, и после сканирования индекса нужно дополнительно сканировать полученные строки для перепроверки
          2. **Медленный поиск подстрок** вытекает из предыдущей проблемы
          3. **Медленная сортировка по времени** тоже вытекает из первой проблемы: GIN не хранит связанную информацию в самом индексе, из-за чего нужно дополнительно сканировать полученные строки
     2. Проблемы решаются за счёт хранения позиционной информации в индексе, что ускоряет полнотекстовый поиск, но замедляет построение индекса и операции вставки

### `INCLUDE` при объявлении индекса
1. `INCLUDE` - это команда, которая позволяет включать дополнительные столбцы в индекс.
2. Поиск по дополнительным столбцам не ускоряется, но при `INDEX ONLY SCAN` индекс может брать данные по дополнительным столбцам из индекса и не ходить в таблицу

### [Стратегии джоина](https://habr.com/ru/articles/560834/)
- **Nested loop** - декартово произведение (каждая строка первой таблицы сравнивается с каждой строкой второй таблицы, и производится проверка по предикату, сложность $O(N^2)$)
- **Merge hash** - переcечение (производится сортировка обеих таблиц по ключу объединения, и объединение выполняется в один проход (каждой таблице назначаются сдвигающиеся счётчики), сложность $O(N*logN)$)
- **Hash join** - чёткое сопоставление (подходит для больших наборов данных. Для каждого из списков считается  хеш ключа, который используется при объединении), как-то так: ![image](Static/4.hash-join.png) (сначала считаются хеши всех строк из первой таблицы, затем для каждой строки из второй таблицы производится сопоставление по хешу уже её ключа)

## TOAST
1. **TOAST** (The Oversized-Attribute Storage Technique) - это механизм хранения больших данных в PostgreSQL.
2. Позволяет хранить данные, которые превышают размер страницы таблицы (обычно 8КБ, *можно установить в пределах 32КБ при сборке сервера, но почти никто этим не занимается*): большие тексты, изображения, видео, бинарные файлы и т.д.
     1. Нужен из-за того, что строку, не влезающую в страницу, нельзя продолжить на другой странице
     2. Может использовать различные алгоритмы сжатия для уменьшения размера хранимых данных (*традиционный PGLZ и более современный LZ4*)
3. Может использовать (и комбинировать) следующие техники:
     1. Сжатие, чтобы строка таки влезла в страницу
     2. Разрезание на "тосты" и хранение их в отдельной служебной таблице (находится в схеме `pg_toast`)
          1. Вместе со служебной таблицей всегда создаётся toast-индекс, используемый для доступа к фрагментам строк
4. Если у таблицы есть потенциально большие атрибуты (столбцы типа numeric или text), служебная таблица будет создана несмотря ни на что
5. Для индексов TOAST предоставляет только сжатие, что накладывает ограничение на размер индексируемых ключей
6. Стратегии:
     1. **plain** - TOAST не используется (применяется для заведомо коротких типов данных типа integer)
     2. **extended** - допускается сжатие и хранение в служебной таблице
     3. **external** - хранение несжатых данных в служебной таблице
     4. **main** - данные сначала сжимаются, и только если это не помогает, отправляются в служебную таблицу

## Чем отличается Explain & Explain Analyze? Как определяется scan explain analyze?
1. `Explain` показывает план выполнения запроса, но не выполняет запрос.
2. `Explain Analyze` выполняет запрос и показывает план выполнения запроса, а также время выполнения и количество строк, обработанных на каждом этапе.
3. `Explain Analyze` необходим для определения скорости выполнения запроса и оптимизации запроса
4. Если есть индекс, используется `INDEX SCAN`. Если ещё и нужные данные могут быть вытащены из самого индекса без необходимости лезть в таблицу, используется `INDEX ONLY SCAN`. Если индекса нет, используется `SEQ SCAN`, и производится проверка каждой строки в таблице.

## Как с помощью EXPLAIN ANALYZE проверить скорость вставки, но при этом не оборачивать в транзакцию?
1. Просто не оборачивать в транзакцию: `EXPLAIN ANALYZE INSERT INTO таблица (поле1, поле2) VALUES ('значение1', 'значение2');`. Это не круто, потому что строка будет вставлена, а нам нужно проверить только скорость вставки. **Смысл не оборачивать в транзакцию?**
2. обернуть в `INSERT INTO SELECT`

## WAL
1. **WAL** (Write-Ahead Logging) - **журнал предзаписи**, механизм хранения журнала изменений в базе данных. Постоянно писать обновлённые страницы на жёсткий диск дорого, поэтому каждое действие с БД записывается в журнал, содержащий минимальную информацию, необходимую для повторения действия
2. Необходим для обеспечения целостности данных и восстановления базы данных в случае сбоя.
3. Как выглядит
     1. ![image](Static/4.wal-internals.png)
     2. Логически журнал можно представить себе как последовательность записей различной длины. Каждая запись содержит _данные_ о некоторой операции, предваренные стандартным _заголовком_. В заголовке, в числе прочего, указаны:
          1. номер транзакции, к которой относится запись;
          2. менеджер ресурсов — компонент системы, ответственный за запись;
          3. контрольная сумма (CRC) — позволяет определить повреждение данных;
          4. длина записи и ссылка на предыдущую запись.
     3. Физически представляет собой файлы в каталоге *pg_wal*. Записи используют один файл за раз: когда файл кончается, начинает использоваться следующий
4. Принцип работы только что добавленных строк:
     1. Только что записанные данные обязательно попадают не только в журнал, но и в основную базу. Только не сразу на диск, а сначала в буферный кеш. Вот из буферного кеша они и читаются.
     2. А вот если сервер упадет, тогда не дошедшие до диска данные будут восстановлены из журнала.
5. Что записывается
     1. изменение страниц в буферном кеше (как правило, это страницы таблиц и индексов) — так как измененная страница попадает на диск не сразу;
     2. фиксация и отмена транзакций — изменение статуса происходит в буферах XACT и тоже попадает на диск не сразу;
     3. файловые операции (создание и удаление файлов и каталогов, например, создание файлов при создании таблицы) — так как эти операции должны происходить синхронно с изменением данных.
6. В журнал не записываются:
     1. операции с нежурналируемыми (unlogged) таблицами — их название говорит само за себя;
     2. операции с временными таблицами — нет смысла, поскольку время жизни таких таблиц не превышает времени жизни создавшего их сеанса.
7. Уровни (параметр `wal_level`)
     1. `minimal` - минимальный набор информации, нужный для восстановления после сбоя или принудительного выключения
          1.  Для экономии места операции, связанные с массовой обработкой данных (такие, как `CREATE TABLE AS SELECT` или `CREATE INDEX`), не записываются в журнал. Вместо этого необходимые данные сразу пишутся на диск, а новый объект добавляется в системный каталог и становится видимым при фиксации транзакции.
          2. Если сбой происходит в процессе выполнения операции, уже записанные данные остаются невидимыми и не нарушают согласованности. Если же сбой происходит после того, как операция завершилась, все необходимое уже попало на диск и не нуждается в журналировании.
     2. `replica` - достаточное для архивации и репликации количество данных
          1. Нужно для восстановления системы из резервной копии
          2. Дополнительно хранит информацию о блокировках и текущих транзакциях - а вообще хранит **[все](https://habr.com/ru/companies/postgrespro/articles/461523/)** операции
     3. `logical` - обеспечивает возможность работы логического декодирования и логической репликации
          1. Почти ничем не отличается от `replica`: добавляются записи, относящиеся к источникам репликации (replication origins), и произвольные логические записи, которые могут добавлять в журнал приложения

## Hypertable
1. Расширение таблиц в постгре, предназначенное для автоматического разделения данных по времени. Работают так же, как и обычные таблицы, но добавляют *некоторые* особенности, упрощающие работу
2. Повышают производительность чтения и вставки данных
3. Состоят из дочерних таблиц (чанков). Каждый чанк содержит данные только за свой промежуток времени

## Альтернативные способы подсчета записей
1. `SUM(CASE WHEN условие THEN 1 ELSE 0 END)`
2. `LENGTH(ARRAY_AGG(поле))`
3. `CARDINALITY(ARRAY_AGG(поле))`: Returns the total number of elements in the array, or 0 if the array is empty. `cardinality(ARRAY[[1,2],[3,4]])` → `4`

## ANALYZE (что конкретно делает)
1. Собирает статистику о содержимом таблиц БД и помещает её в каталог `pg_statistics`
2. Статистика обычно содержит самые часто используемые значения по каждому столбцу и гистограмму, показывающую примерное распределение по каждому столбцу. Они могут быть опущены для столбцов, которые демон посчитал неинтересными (например, столбцы с навешенным `UNIQUE`, в которых по определению не может быть самых часто используемых значений)
3. Для больших столбцов аналитика делается по некоторой выборке строк

## Сделал EXPLAIN ANALYZE, что там: SCAN или INDEX SCAN?
Если в результате `EXPLAIN ANALYZE` я вижу `SCAN`, это означает, что база данных производит полное сканирование таблицы, т.е. она проверяет каждую строку таблицы, чтобы найти необходимые данные. Это может быть медленно, особенно для больших таблиц. Если же я вижу `INDEX SCAN`, это означает, что база данных использует индекс для поиска необходимых данных, что обычно намного быстрее

## [Блокировки](https://postgrespro.ru/docs/postgresql/17/explicit-locking)
Вне зависимости от вида блокировки они отличаются друг от друга только тем, с какими блокировками они конфликтуют
### Уровня таблицы (даже если блокировка имеет в названии `ROW`, она работает на уровне таблицы)
Виды
1. `ACCESS SHARE` получает любой запрос, который **читает, но не изменяет таблицу**
2. `ROW SHARE` устанавливается командой `SELECT` для всех таблиц, для которых задано указание `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE` или `FOR KEY SHARE` (в дополнение к блокировкам `ACCESS SHARE` для любых других таблиц, задействованных без каких-либо явных указаний блокировки `FOR .. .`)
3. `ROW EXCLUSIVE`. Вообще говоря, блокировку в этом режиме получает любая команда, которая _изменяет данные_ в таблице.
4. `SHARE UPDATE EXCLUSIVE`. Этот режим защищает таблицу от параллельного изменения схемы и запуска процесса `VACUUM`. Запрашивается командами `VACUUM` (без `FULL`), `ANALYZE`, `CREATE INDEX CONCURRENTLY`, `CREATE STATISTICS`, `COMMENT ON`, `REINDEX CONCURRENTLY` и некоторыми формами `ALTER INDEX` и `ALTER TABLE`.
5. `SHARE`. Этот режим защищает таблицу от параллельного изменения данных. Запрашивается командой `CREATE INDEX` (без параметра `CONCURRENTLY`).
6. `SHARE ROW EXCLUSIVE`. Этот режим защищает таблицу от параллельных изменений данных и при этом он является самоисключающим, так что такую блокировку может получить только один сеанс. Запрашивается командой `CREATE TRIGGER` и некоторыми формами `ALTER TABLE`
7. `EXCLUSIVE`. Этот режим совместим только с блокировкой `ACCESS SHARE`, то есть параллельно с транзакцией, получившей блокировку в этом режиме, допускается только чтение таблицы. Запрашивается командой `REFRESH MATERIALIZED VIEW CONCURRENTLY`.
8. `ACCESS EXCLUSIVE`. Этот режим гарантирует, что кроме транзакции, получившей эту блокировку, никакая другая транзакция не может обращаться к таблице каким-либо способом. Запрашивается командами `DROP TABLE`, `TRUNCATE`, `REINDEX`, `CLUSTER`, `VACUUM FULL` и `REFRESH MATERIALIZED VIEW` (без `CONCURRENTLY`). Блокировку на этом уровне запрашивают также многие виды `ALTER INDEX` и `ALTER TABLE`. В этом режиме по умолчанию запрашивают блокировку и операторы `LOCK TABLE`, если явно не выбран другой режим.
**Только блокировка `ACCESS EXCLUSIVE` блокирует оператор `SELECT` (без `FOR UPDATE/SHARE`).**

| -------------------------------- | :---------------------------: | :---------: | :---------: | :------------------: | :-----: | :---------------: | :-----: | :------------: |
|                                  |        `ACCESS SHARE`         | `ROW SHARE` | `ROW EXCL.` | `SHARE UPDATE EXCL.` | `SHARE` | `SHARE ROW EXCL.` | `EXCL.` | `ACCESS EXCL.` |
| `ACCESS SHARE`                   |                               |             |             |                      |         |                   |         |       X        |

| `ROW EXCL.`                      |                               |             |             |                      |    X    |         X         |    X    |       X        |

### Уровня строки (влияют только на запись и не блокируют чтение)
Виды
- `FOR UPDATE`
     - В режиме `FOR UPDATE` строки, выданные оператором `SELECT`, блокируются как для изменения. При этом они защищаются от блокировки, изменения и удаления другими транзакциями до завершения текущей. То есть другие транзакции, пытающиеся выполнить `UPDATE`, `DELETE`, `SELECT FOR UPDATE`, `SELECT FOR NO KEY UPDATE`, `SELECT FOR SHARE` или `SELECT FOR KEY SHARE` с этими строками, будут заблокированы до завершения текущей транзакции; и наоборот, команда `SELECT FOR UPDATE` будет ожидать окончания параллельной транзакции, в которой выполнилась одна из этих команд с той же строкой, а затем установит блокировку и вернёт изменённую строку (или не вернёт, если она была удалена). Однако в транзакции `REPEATABLE READ` или `SERIALIZABLE` возникнет ошибка, если блокируемая строка изменилась с момента начала транзакции
     - Режим блокировки `FOR UPDATE` также запрашивается на уровне строки любой командой `DELETE` и командой `UPDATE`, изменяющей значения определённых столбцов. В настоящее время блокировка с `UPDATE` касается столбцов, по которым создан уникальный индекс, применимый в качестве внешнего ключа (так что на частичные индексы и индексы выражений это не распространяется), но в будущем это может поменяться.
- `FOR NO KEY UPDATE`
     - Действует подобно `FOR UPDATE`, но запрашиваемая в этом режиме блокировка слабее: она не будет блокировать команды `SELECT FOR KEY SHARE`, пытающиеся получить блокировку тех же строк. Этот режим блокировки также запрашивается любой командой `UPDATE`, которая не требует блокировки `FOR UPDATE`.
- `FOR SHARE`
     - Действует подобно `FOR NO KEY UPDATE`, за исключением того, что для каждой из полученных строк запрашивается разделяемая, а не исключительная блокировка. Разделяемая блокировка не позволяет другим транзакциям выполнять с этими строками `UPDATE`, `DELETE`, `SELECT FOR UPDATE` или `SELECT FOR NO KEY UPDATE`, но допускает `SELECT FOR SHARE` и `SELECT FOR KEY SHARE`.
- `FOR KEY SHARE`
     - Действует подобно `FOR SHARE`, но устанавливает более слабую блокировку: блокируется `SELECT FOR UPDATE`, но не `SELECT FOR NO KEY UPDATE`. Блокировка разделяемого ключа не позволяет другим транзакциям выполнять команды `DELETE` и `UPDATE`, только если они меняют значение ключа (но не другие `UPDATE`), и при этом допускает выполнение команд `SELECT FOR NO KEY UPDATE`, `SELECT FOR SHARE` и `SELECT FOR KEY SHARE`.
PostgreSQL не держит информацию об изменённых строках в памяти, так что никаких ограничений на число блокируемых строк нет. Однако блокировка строки может повлечь запись на диск, например, если `SELECT FOR UPDATE` изменяет выбранные строки, чтобы заблокировать их, при этом происходит запись на диск.

| -------------------------------- | ------------------------ | ----------- | ------------------- | ------------ |
|                                  | `FOR KEY SHARE`          | `FOR SHARE` | `FOR NO KEY UPDATE` | `FOR UPDATE` |

### Уровня страницы
В дополнение к блокировкам на уровне таблицы и строк, для управления доступом к страницам таблиц в общих буферах используются блокировки на уровне страниц, исключительные и разделяемые.
Эти блокировки освобождаются немедленно после выборки или изменения строк.
Разработчикам приложений обычно можно не задумываться о блокировках страниц, здесь они упоминаются только для полноты картины.

## Heap only tuples (HOT)
1. Правильный ответ: **Не надо навешивать индексы после обновления**
2. Из-за того, что держать в индексе ссылки на все версии строки неэффективно (нужно постоянно обновлять индекс, даже если изменились поля, не входящие в этот индекс; в индексах накапливаются исторические версии строк, которые тоже надо чистить), используется **hot-update** (Heap-Only Tuple update). Оно применяется в следующих случаях:
     1. у таблицы нет индексов (любое обновление будет hot-update)
     2. индексы есть, но обновляемые столбцы не используются ни в одном из них
     3. обновляемые столбцы есть в индексах, но их значения не поменялись
3. "Использованием в индексе" называется любое упоминание столбца при создании индекса. Исключением являются BRIN-индексы: они не содержат ссылок на табличные строки и не мешают hot-обновлениям
4. При hot-обновлении в индексной странице присутствует только одна запись с идентификатором самой первой версии табличной строки. Остальные связываются в цепочку при помощи `ctid` в заголовках версий
5. **Не понял до конца, как оно работает,  лучше не закапываться**
6. Как я понял, под heap подразумевается таблица, а под tuple - версии строк в ней

## Агрегации Pipeline, Индексы, Relations, Репликация
1. **Агрегации Pipeline**: это механизм обработки данных в MongoDB, который позволяет выполнять сложные запросы и агрегации данных. `db.collection.aggregate()` An aggregation pipeline consists of one or more [stages](https://www.mongodb.com/docs/manual/reference/operator/aggregation-pipeline/#std-label-aggregation-pipeline-operator-reference) that process documents:
     1. Each stage performs an operation on the input documents. For example, a stage can filter documents, group documents, and calculate values.
     2. The documents that are output from a stage are passed to the next stage.
     3. An aggregation pipeline can return results for groups of documents. For example, return the total, average, maximum, and minimum values.
2. **Индексы в MongoDB**: Indexes support efficient execution of queries in MongoDB. Without indexes, MongoDB must scan every document in a collection to return query results. If an appropriate index exists for a query, MongoDB uses the index to limit the number of documents it must scan

## Bulk операция в джанго?
1. возможность выполнить несколько операций с данными за один запрос к базе данных. Это может ускорить выполнение операций с данными, особенно при работе с большими объемами данных.
2. В Django можно использовать bulk операции с помощью методов `bulk_create()`, `bulk_update()`, `bulk_delete()` и других. Например
     ```python
     from django.db import models
     # Создание нескольких объектов за один запрос
     objects = [
        MyModel(name='obj1'),
        MyModel(name='obj2'),
        MyModel(name='obj3')
     ]
     MyModel.objects.bulk_create(objects)
     
     # Обновление нескольких объектов за один запрос
     objects = MyModel.objects.filter(name__startswith='obj')
     for obj in objects:
          obj.name = 'new_name'
     MyModel.objects.bulk_update(objects, fields=['name'])
     
     # Удаление нескольких объектов за один запрос
     objects = MyModel.objects.filter(name__startswith='obj') 
     MyModel.objects.bulk_delete(objects)
     ```

## Джоины в рамках контейнера MongoDB
возможность объединить данные из нескольких коллекций (аналог таблиц в реляционных базах данных) в рамках одного запроса.
В MongoDB можно использовать джоины с помощью оператора `$lookup`. Например:
```JS (not really)
db.collection1.aggregate([{
     $lookup: {
          from: "collection2",
          localField: "field1",
          foreignField: "field2",
          as: "result"
     }
}])
```
Этот запрос объединяет данные из коллекций `collection1` и `collection2` по полю `field1` и `field2` соответственно

Можно использовать джоины с помощью операторов `$lookup`, `$merge`, `$union` и других
```JS (not really)
db.collection1.aggregate([
     {
          $lookup: {
               from: "collection2",
               localField: "field1",
               foreignField: "field2",
               as: "result"
          }
     },
     {
          $merge: {
               into: "collection3",
               on: "field3",
               as: "result2"
          }
     }
])
```
Этот запрос объединяет данные из коллекций `collection1`, `collection2` и `collection3` по полям `field1`, `field2` и `field3` соответственно

## Масштабируемость в монго
1. Масштабируемость в Монго (MongoDB) - это возможность увеличить производительность и масштаб базы данных по мере роста количества данных и пользователей.
2. В MongoDB можно использовать несколько методов для масштабирования базы данных, таких как:
     1. Шардирование (sharding): разделение данных на несколько фрагментов (шардов) и распределение их между несколькими серверами.
     2. Репликация (replication): создание копий базы данных на нескольких серверах для обеспечения доступности данных в случае сбоя одного из серверов.
     3. Кластеризация (clustering): создание кластера серверов, которые могут работать вместе для обеспечения доступности данных.
     4. Load balancing: распределение нагрузки между несколькими серверами для обеспечения доступности данных
