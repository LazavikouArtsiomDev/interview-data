1. Django: объект QuerySet. Что это, как использовать?    
    1. объект, представляющий собой набор объектов определенной модели
    2. `Model.objects.all()` , `filter` , `order_by` , `exclude` и т.д.
    3. `QuerySet` лениво выполняет запросы к базе данных. Это значит, что запрос выполняется только тогда, когда данные действительно нужны
    4. `QuerySet` не только представляет набор объектов, но также инкапсулирует логику построения SQL-запроса. Это позволяет конструировать сложные запросы путем последовательного применения методов (method chaining).
    5. после первого обращения к QuerySet, результаты сохраняются в памяти и повторные обращения не вызывают новых запросов к БД
2. Сигналы в Джанге – что это? Какой это паттерн проектирования?    
    1. реализация паттерна “Наблюдатель”. Они позволяют реагировать на определенные события, происходящие в приложении, например, сохранение объекта, удаление объекта или изменение значения поля
    2. Когда происходит такое событие, Django отправляет сигнал. Другие части приложения могут "подписаться" на этот сигнал и выполнить определенный код в ответ на него
    3. Нужно упомянуть встроенные типы сигналов: `pre_save`, `post_save`, `pre_delete`, `post_delete`, `pre_init`, `post_init`, `m2m_changed`
    4. сигналы могут нарушать принцип явности кода и усложнять отладку
```python
from django.db.models.signals import post_save
from django.dispatch import receiver
from django.core.mail import send_mail

# Декоратор @receiver указывает, что функция является обработчиком сигнала
@receiver(post_save, sender=User)
def send_welcome_email(sender, instance, created, **kwargs):
    """
    Отправляет приветственное письмо новым пользователям
    """
    if created:  # Только для новых пользователей
        send_mail(
            subject='Welcome!',
            message=f'Welcome to our site, {instance.username}!',
            from_email='noreply@example.com',
            recipient_list=[instance.email],
        )

# Альтернативный способ подключения сигнала
def my_callback(sender, instance, **kwargs):
    print("Model saved!")

# Подключение сигнала программно
post_save.connect(my_callback, sender=User)
```

5. datamapper vs activerecord?    
    1. два разных паттерна
    2. **Active Record:** Каждый объект модели напрямую связан с таблицей в базе данных и содержит методы для работы с этой таблицей. Этот подход проще в использовании, но может привести к более тесной связи между кодом приложения и базой данных.
         1. толстая модель
    3. **Data Mapper:** Объекты модели и база данных разделены слоем маппера, который отвечает за преобразование данных между объектами и базой данных. Этот подход сложнее, но обеспечивает лучшую разделенность кода и большую гибкость.
         1. модель представляет только то, как таблица выглядит в бд
     4. **Active Record проще, Data Mapper гибче**
```python
          # Модель без логики работы с БД
          class User:
              def __init__(self, name: str, email: str):
                  self.name = name
                  self.email = email
          
          # Отдельный класс для маппинга
          class UserMapper:
              def __init__(self, db_session):
                  self.session = db_session
              
              def save(self, user: User):
                  self.session.execute(
                      "INSERT INTO users (name, email) VALUES (?, ?)",
                      user.name, user.email
                  )
              
              def find_by_email(self, email: str) -> Optional[User]:
                  result = self.session.query(
                      "SELECT * FROM users WHERE email = ?", 
                      email
                  )
                  if result:
                      return User(**result)
                  return None
          
          # Использование
          user = User(name="John", email="john@example.com")
          mapper = UserMapper(db_session)
          mapper.save(user)  # Маппер управляет сохранением
```

13. Что "сериализатор" (serializer) и "парсер" (parser)?    
    1. **Сериализатор:** Компонент, который преобразует объекты Python (например, модели Django) в форматы данных, такие как JSON или XML. Это используется для передачи данных по сети или для сохранения их в других форматах. Сериализаторы также выполняют обратное преобразование - из данных в объекты Python. В Django REST framework сериализаторы играют ключевую роль в представлении данных API
    2. **Парсер:** Компонент, который разбирает данные, полученные из запроса, например, в формате JSON или XML, и преобразует их в структуры данных Python. Django REST framework предоставляет различные парсеры для работы с разными форматами данных

15. Что такое MVC? Для Django - сравнить с MTV    
    1. **MVC (Model-View-Controller):** Это архитектурный паттерн, разделяющий приложение на три взаимосвязанные части:
        1. **Model (Модель):** Работа с данными (база данных, API и т.д.).
        2. **View (Представление):** Отображение данных пользователю (HTML, JSON и т.д.).
        3. **Controller (Контроллер):** Обработка запросов пользователя, взаимодействие с моделью и выбор представления.
    2. **MTV (Model-Template-View) в Django:** Это вариация MVC, адаптированная под Django:
        1. **Model (Модель):** Аналогично MVC – работа с данными.
        2. **Template (Шаблон):** Определяет, _как_ данные будут представлены пользователю (HTML). Аналог View в MVC.
        3. **View (Представление):** Обрабатывает запросы, взаимодействует с моделью и выбирает шаблон для отображения. Аналог Controller в MVC.
        4. Особенности Django:
             1. В Django View (представление) содержит бизнес-логику, которая в MVC находилась бы в Controller
             2. Template в Django более ограничен в функциональности по сравнению с View в MVC
             3. Django следует принципу "толстых моделей" - большая часть бизнес-логики находится в моделях
             4. В Django шаблоны являются более пассивными и не содержат сложной логики

19. Что такое Django Channels?    
    1. расширение Django, которое позволяет обрабатывать асинхронные запросы, такие как WebSockets
    2. as well as the ability to run code after a response has been sent for things like thumbnailing or background calculation
        1. Easy HTTP long-poll support for thousands of clients at once
        2. Full session and auth support for WebSockets
        3. Automatic user login for WebSockets based on site cookies
        4. Built-in primitives for mass triggering of events (chat, live blogs, etc.)
        5. Zero-downtime deployment with browsers paused while new workers spin up
        6. Optional low-level HTTP control on a per-URL basis
        7. Extendability to other protocols or event sources (e.g. WebRTC, raw UDP, SMS)
     ```python
     # routing.py
     from django.urls import re_path
     from . import consumers
     
     websocket_urlpatterns = [
         re_path(r'ws/chat/(?P<room_name>\w+)/$', 
              consumers.ChatConsumer.as_asgi()
          ),
     ]
     
     # consumers.py
     from channels.generic.websocket import AsyncWebsocketConsumer
     import json
     
     class ChatConsumer(AsyncWebsocketConsumer):
         async def connect(self):
             self.room_name = self.scope['url_route']['kwargs']['room_name']
             self.room_group_name = f'chat_{self.room_name}'
     
             # Присоединяемся к группе комнаты
             await self.channel_layer.group_add(
                 self.room_group_name,
                 self.channel_name
             )
             await self.accept()
     
         async def disconnect(self, close_code):
             # Покидаем группу
             await self.channel_layer.group_discard(
                 self.room_group_name,
                 self.channel_name
             )
     
         async def receive(self, text_data):
             text_data_json = json.loads(text_data)
             message = text_data_json['message']
     
             # Отправляем сообщение в группу
             await self.channel_layer.group_send(
                 self.room_group_name,
                 {
                     'type': 'chat_message',
                     'message': message
                 }
             )
     
         async def chat_message(self, event):
             message = event['message']
             # Отправляем сообщение в WebSocket
             await self.send(text_data=json.dumps({
                 'message': message
             }))
     ```

20. Зачем необходим метод dispatch во View в Django?    
    1. Метод `dispatch` в Django View – это центральная точка входа для обработки запроса. Он отвечает за определение HTTP-метода запроса (GET, POST, PUT, DELETE и т.д.) и вызов соответствующего обработчика (например, `get()`, `post()`, `put()`, `delete()`). `dispatch` также выполняет общую логику, такую как проверка прав доступа или обработка middleware, перед вызовом конкретного обработчика
    2. Ключевые аспекты dispatch:
         1. Централизованная обработка запросов
         2. Возможность добавления общей логики для всех методов
         3. Поддержка декораторов на уровне класса
         4. Обработка ошибок и проверка прав доступа
         5. Маршрутизация к конкретным обработчикам методов
     ```python
     from django.views import View
     from django.utils.decorators import method_decorator
     from django.contrib.auth.decorators import login_required
     
     class ProductView(View):
         @method_decorator(login_required)
         def dispatch(self, request, *args, **kwargs):
             # Общая логика для всех методов
             self.product = self.get_product(kwargs.get('pk'))
             if not self.product:
                 return HttpResponseNotFound()
                 
             # Проверка прав доступа
             if not request.user.has_perm('products.view_product'):
                 return HttpResponseForbidden()
                 
             # Вызов родительского dispatch для обработки HTTP-метода
             return super().dispatch(request, *args, **kwargs)
     
         def get(self, request, *args, **kwargs):
             return render(request, 'product_detail.html', {'product': self.product})
     
         def post(self, request, *args, **kwargs):
             # Обработка POST-запроса
             if 'delete' in request.POST:
                 self.product.delete()
                 return redirect('product_list')
     ```

27.  Model Inheritance в Django
    1. Django поддерживает три типа наследования моделей:
        1. **Abstract base classes:** Абстрактная базовая модель не создает свою таблицу в базе данных. Она служит для определения общих полей и методов для дочерних моделей. Полезно для извлечения общего функционала. Объявляется при помощи `abstract = True` в `Meta`
        2. **Multi-table inheritance:** Каждая модель в иерархии наследования имеет свою таблицу в базе данных. Дочерние модели наследуют поля от родительской модели. Это наиболее гибкий, но и наименее производительный тип наследования. Объявляется при помощи простого наследования, в БД будут созданы две таблицы. У дочерней таблицы будут только новые поля и внешний ключ на родительскую таблицу
        3. **Proxy models:** Прокси-модель не создает новую таблицу в базе данных. Она использует таблицу родительской модели, но позволяет изменить поведение модели, например, добавить новые методы или менеджеры.
          ```python
          class PublishedArticleManager(models.Manager):
               def get_queryset(self):
                    return super().get_queryset().filter(status='published') 
          
          class PublishedArticle(Article):
               objects = PublishedArticleManager()
               class Meta:
                    proxy = True # Это делает модель прокси
               def publish(self):
                    self.status = 'published'
                    self.save()
          ```

28.  Что такое sync_to_async в Django?    
    1. `sync_to_async` – это функция-декоратор в Django, которая позволяет вызывать синхронный код (например, функции, работающие с Django ORM) из асинхронного контекста. Это необходимо, потому что Django ORM по умолчанию синхронный, а работа с асинхронными запросами (например, WebSockets) требует асинхронного кода. `sync_to_async` "обертывает" синхронный код в асинхронную функцию, позволяя использовать его в асинхронных представлениях
          ```python
          from channels.db import database_sync_to_async
          from channels.generic.websocket import AsyncWebsocketConsumer
          from django.db import transaction
          
          class ChatConsumer(AsyncWebsocketConsumer):
              async def connect(self):
                  self.user = self.scope["user"]
                  self.room_id = self.scope['url_route']['kwargs']['room_id']
                  
                  # Проверяем доступ к комнате асинхронно
                  if await self.can_access_room():
                      await self.accept()
                  else:
                      await self.close()
          
              @database_sync_to_async
              def can_access_room(self):
                  try:
                      # Синхронный код Django ORM
                      room = ChatRoom.objects.get(id=self.room_id)
                      return room.members.filter(id=self.user.id).exists()
                  except ChatRoom.DoesNotExist:
                      return False
          
              async def receive(self, text_data):
                  # Сохраняем сообщение асинхронно
                  message = await self.save_message(text_data)
                  if message:
                      # Отправляем сообщение всем участникам
                      await self.channel_layer.group_send(
                          f"room_{self.room_id}",
                          {
                              "type": "chat.message",
                              "message": message
                          }
                      )
          
              @database_sync_to_async
              def save_message(self, text_data):
                  # Используем транзакцию в синхронном коде
                  with transaction.atomic():
                      message = Message.objects.create(
                          room_id=self.room_id,
                          user=self.user,
                          content=text_data
                      )
                      return {
                          'id': message.id,
                          'content': message.content,
                          'user': message.user.username
                      }
          ```

29.  Что такое select_related и prefetch_related в Django ORM?    
    1. методы оптимизации запросов к базе данных в Django ORM, которые позволяют уменьшить количество запросов при работе со связанными моделями.
    2. **`select_related`:** Используется для связанных моделей с отношением "один-к-одному" или "много-к-одному". Он выполняет JOIN-запрос к базе данных, получая данные связанных моделей в одном запросе.
     1. ==проверить "один-ко-многим": 1 человек, много машин==
```python
# Проблема N+1 запросов:
def inefficient_view(request):
     # Это создаст N+1 запросов: 1 для книг и N для авторов
     books = Book.objects.all()
     for book in books:
          print(f"{book.title} by {book.author.name}") # Каждое обращение к author создаст новый запрос

# Решение с select_related:
def efficient_view_select(request):
     # Создаст только 1 запрос с JOIN
     books = Book.objects.select_related('author').all()
     for book in books:
          print(f"{book.title} by {book.author.name}") # Данные уже загружены

# Работа с M2M отношениями:
def efficient_view_prefetch(request):
     # Создаст 2 запроса: один для книг и один для всех связанных категорий
     books = Book.objects.prefetch_related('categories').all()
     for book in books:
          categories = ", ".join([
               c.name for c in book.categories.all()
          ])
          print(f"{book.title}: {categories}")
```

- **`prefetch_related`:** Используется для связанных моделей с отношением "много-ко-многим" или для случаев, когда `select_related` не подходит. Он выполняет отдельные запросы для каждой связанной модели, а затем "склеивает" результаты в Python.
     - При использовании select_related:
         - Увеличивает объем получаемых данных
         - Может замедлить начальный запрос
         - Экономит запросы при доступе к связанным объектам
         - Лучше всего работает с прямыми связями (ForeignKey, OneToOne)
     - При использовании prefetch_related:
         - Выполняет отдельные запросы для связанных данных
         - Объединяет результаты в Python
         - Позволяет работать со сложными отношениями (ManyToMany)
         - Требует внимательного подхода к фильтрации
     - Объект Prefetch предоставляет:
         - Возможность предварительной фильтрации
         - Сохранение результатов в специальный атрибут
         - Возможность использования дополнительных QuerySet методов
         - Более точный контроль над процессом предзагрузки
30.  Проблем с фильтрацией при использовании метода prefetch_related.?    
    1. фильтрация происходит _после_ того, как данные уже получены из базы данных. Это значит, что если вы фильтруете связанные объекты, `prefetch_related` все равно загрузит все связанные объекты, а затем отфильтрует их
    2. Для фильтрации связанных объектов _перед_ запросом к базе данных лучше использовать `Prefetch` object с `queryset` аргументом
```python
from django.db.models import Prefetch

class Book(models.Model):
    title = models.CharField(max_length=200)
    published_date = models.DateField()
    reviews = models.ManyToManyField('Review')

class Review(models.Model):
    text = models.TextField()
    rating = models.IntegerField()
    is_verified = models.BooleanField(default=False)

# Неэффективный способ (загружает все обзоры, потом фильтрует):
def inefficient_filtering(request):
    books = Book.objects.prefetch_related('reviews').all()
    for book in books:
        # Это игнорирует prefetch и делает новый запрос
        verified_reviews = book.reviews.filter(is_verified=True)

# Эффективное решение с Prefetch:
def efficient_filtering(request):
    verified_reviews = Prefetch(
        'reviews',
        queryset=Review.objects.filter(is_verified=True),
        to_attr='verified_reviews_list'
    )
    
    books = Book.objects.prefetch_related(verified_reviews).all()
    
    for book in books:
        # Используем предварительно отфильтрованные обзоры
        for review in book.verified_reviews_list:
            print(f"{book.title}: {review.rating}")

# Более сложный пример с несколькими Prefetch:
def complex_prefetch(request):
    books = Book.objects.prefetch_related(
        Prefetch(
            'reviews',
            queryset=Review.objects.filter(is_verified=True),
            to_attr='verified_reviews'
        ),
        Prefetch(
            'reviews',
            queryset=Review.objects.filter(rating__gte=4),
            to_attr='high_rated_reviews'
        )
    ).all()
```

38. Как можно решить проблему N+1 с помощью SQLAlchemy?    
    1. **`joinedload`:** Выполняет JOIN-запрос, получая данные связанных объектов в одном запросе. Аналогично `select_related` в Django.
    2. **`subqueryload`:** Выполняет отдельный подзапрос для получения данных связанных объектов.
    3. **`selectinload`:** Выполняет два запроса: один для получения основных объектов, а второй для получения всех связанных объектов с использованием `IN` оператора.
     ```python
     from sqlalchemy.orm import joinedload, subqueryload, selectinload
     
     # Пример решения N+1 с помощью различных методов загрузки
     def get_users_with_posts(session):
         # joinedload - загрузка в одном запросе с JOIN
         users = session.query(User).options(joinedload(User.posts)).all()
         
         # subqueryload - загрузка подзапросом
         users = session.query(User).options(subqueryload(User.posts)).all()
         
         # selectinload - загрузка с использованием IN
         users = session.query(User).options(selectinload(User.posts)).all()
     ```

39. Перечислите и опишите методы загрузки отношений SQLALchemy.    
    1. **`lazy="select"` (по умолчанию):** Связанные объекты загружаются при первом обращении к ним. Это может привести к проблеме N+1.
    2. **`lazy="joined"`:** Связанные объекты загружаются с помощью JOIN-запроса. Аналогично `joinedload`.
         1. `SELECT users.id, users.name, posts.id, posts.title FROM users LEFT JOIN posts ON users.id = posts.user_id`
    3. **`lazy="subquery"`:** Связанные объекты загружаются с помощью подзапроса. Аналогично `subqueryload`.
         1. `-- Основной запрос`
         2. `SELECT users.id, users.name FROM users`
         3. `-- Подзапрос для связанных записей`
         4. `SELECT posts.* FROM posts WHERE posts.user_id IN (SELECT .id FROM users)`
    4. **`lazy="selectin"`:** Связанные объекты загружаются с помощью двух запросов и `IN` оператора. Аналогично `selectinload`.
         1. `-- Первый запрос`
         2. `SELECT users.id, users.name FROM users`
         3. `-- Второй запрос`
         4. `SELECT posts.* FROM posts WHERE posts.user_id IN (1, 2, 3)`
    5. **`lazy="dynamic"`:** Возвращает `Query` объект, который можно использовать для дальнейшей фильтрации и сортировки связанных объектов.
    6. **`lazy="noload"`:** Связанные объекты не загружаются.
40. Что разница между параметрами back_ref и back_populate?    
    1. **`backref`:** Создает новое свойство relationship на обратной стороне отношения _автоматически_. Это более простой и удобный способ, но менее гибкий. Вы не можете настроить каскадные операции или другие параметры обратного отношения.
     ```python
     class User(Base):
          __tablename__ = 'users'
          id = Column(Integer, primary_key=True)
          posts = relationship("Post", backref="author")
     class Post(Base):
          __tablename__ = 'posts'
          id = Column(Integer, primary_key=True)
          user_id = Column(Integer, ForeignKey('users.id'))
     ```
    2. **`back_populate`:** Требует _явного_ определения свойства relationship на обеих сторонах отношения. Это более гибкий подход, позволяющий настраивать все параметры обоих отношений, включая каскадные операции, `lazy` loading и другие.

63. Разница stateless и stateful, и для чего они нужны?    
    1. **Stateless (без состояния):** Сервер не хранит информацию о предыдущих запросах клиента. Каждый запрос обрабатывается независимо от других. Это упрощает масштабирование и повышает надежность, но требует передачи всей необходимой информации в каждом запросе. Пример: HTTP.
    2. **Stateful (с состоянием):** Сервер хранит информацию о состоянии клиента между запросами. Это позволяет сохранять контекст и упрощает работу с некоторыми типами приложений, но усложняет масштабирование и снижает надежность. Пример: WebSocket.

68. Caching Strategies?
    1. **Cache-Aside:** Приложение сначала проверяет наличие данных в кэше. Если данные есть, они используются из кэша. Если данных нет, приложение запрашивает их из основного источника данных (например, базы данных), сохраняет в кэше и возвращает клиенту.
    2. **Read-Through:** Кэш находится между приложением и основным источником данных. Приложение всегда запрашивает данные из кэша. Кэш сам проверяет наличие данных и, если их нет, запрашивает из основного источника данных, сохраняет в кэше и возвращает приложению.
    3. **Write-Through:** Приложение записывает данные одновременно и в кэш, и в основной источник данных. Это обеспечивает согласованность данных, но может снизить производительность записи.
    4. **Write-Back (Write-Behind):** Приложение записывает данные только в кэш. Кэш асинхронно записывает данные в основной источник данных. Это повышает производительность записи, но может привести к потере данных в случае сбоя кэша.

88. Что такое сеанс связи? Какой алгоритм использует TCP для доставки?    
    1. логическое соединение между двумя приложениями, которое устанавливается и поддерживается протоколом TCP. 89. Зачем нужен IP-адрес, если MAC-адрес уникален? Разве мы не можем общаться только по MAC-адресу?    
    1. MAC-адрес уникален для каждого сетевого интерфейса и используется для идентификации устройств _в локальной сети_. IP-адрес используется для идентификации устройств _в глобальной сети (Интернет)_. MAC-адреса используются на канальном уровне модели OSI, а IP-адреса – на сетевом уровне. Для связи между разными сетями необходима маршрутизация, которая основана на IP-адресах. MAC-адреса не маршрутизируются.
    2. Проблемы маршрутизации с MAC:
         1. MAC-адреса не иерархические
         2. Невозможно эффективно маршрутизировать трафик между сетями
         3. Каждый роутер должен будет хранить MAC всех устройств в мире
     3. Принципиальные различия:
          1. MAC-адрес = идентификация устройства
          2. IP-адрес = точка подключения к сети
          3. IP позволяет группировать устройства по подсетям

92. В чем отличия между IPv4 и IPv6? Зачем мы мигрируем на IPv6?    
    1. **Длина адреса:** IPv4 использует 32-битные адреса, IPv6 – 128-битные.
    2. **Количество адресов:** IPv4 предоставляет около 4.3 миллиарда адресов, IPv6 – практически неограниченное количество.
    3. **Формат адреса:** IPv4 использует десятичную запись с точками (например, 192.168.1.1), IPv6 – шестнадцатеричную запись с двоеточиями (например, 2001:0db8:85a3:0000:0000:8a2e:0370:7334).
    4. **Автоконфигурация:** IPv6 поддерживает автоконфигурацию адресов, что упрощает настройку сети.
    5. **Встроенная безопасность:** IPv6 имеет встроенную поддержку IPsec, что повышает безопасность.
    6. **Мультикастинг:** IPv6 имеет улучшенную поддержку мультикастинга.
    7. **Миграция на IPv6 необходима из-за исчерпания адресного пространства IPv4**

```python
    print(book.publication_year, book.rating)  # These fields are loaded from the database
```

```python
from django.db import transaction

# Декоратор atomic
@transaction.atomic
def transfer_money(from_account, to_account, amount):
    try:
        # Все операции либо выполнятся полностью, либо откатятся
        from_account.balance -= amount
        from_account.save()
        
        to_account.balance += amount
        to_account.save()
    except Exception as e:
        # Автоматический откат транзакции
        raise

# Контекстный менеджер
def transfer_money_context(from_account, to_account, amount):
    with transaction.atomic():
        from_account.balance -= amount
        from_account.save()
        
        to_account.balance += amount
        to_account.save()

# Настройка на уровне БД

    'default': {
        # Включение atomic requests по умолчанию
        'ATOMIC_REQUESTS': True,
    }
}
```

     2. Часовые пояса

          3. Часовой пояс по умолчанию устанавливается `TIME_ZONE`

134. стратегии расширения модели пользователя
     1. Proxy-модель
          
          ```python
          class MyUser(User):
              class Meta:
                  proxy = True
              
              def custom_method(self):
                  pass
          ```

          1. Только добавление методов
          2. Не меняет структуру БД
     2. One-to-One связь
          
          ```python
          from django.contrib.auth.models import User
          
          class Profile(models.Model):
              user = models.OneToOneField(User, on_delete=models.CASCADE)
              phone = models.CharField(max_length=20)
          ```

          1. Сохраняет стандартную модель User
          2. Можно добавлять дополнительные поля
          3. Удобно для небольших расширений
          4. ==заменить на наследование от модели==
     1. AbstractUser
          ```python
          from django.contrib.auth.models import AbstractUser
          
          class CustomUser(AbstractUser):
              phone = models.CharField(max_length=20)
              
          # settings.py
          AUTH_USER_MODEL = 'myapp.CustomUser'
          ```
          1. Полная кастомизация модели
          2. Можно менять базовые поля
          3. Требует настройки с самого начала проекта
          4. Наследуется от `AbstractBaseUser` (добавляет поля `password` и `last_login` и служебные методы: `save`, `get_username`, `clean` и т.д.) и `PermissionsMixin` (добавляет поля `groups`, `is_superuser` и методы, связанные с разрешениями)
     4. AbstractBaseUser
          ```python
          from django.contrib.auth.models import AbstractBaseUser, PermissionsMixin
          
          class CustomUser(AbstractBaseUser, PermissionsMixin):
              email = models.EmailField(unique=True)
              USERNAME_FIELD = 'email'
          ```
          1. Максимальная гибкость
          2. Полный контроль над моделью
          3. Сложнее в реализации
     5. Рекомендации:
          1. Для новых проектов - AbstractUser
          2. Для существующих - One-to-One связь
