# Паттерны ([опа, ссылка](https://refactoring.guru/design-patterns/catalog))
## Baza
### Определения
**Паттерны** проектирования — это типичные решения для часто встречающихся задач. Они представляют собой шаблоны, которые помогают создавать гибкие, поддерживаемые и масштабируемые системы. Паттерны не являются готовым кодом, а скорее описывают подход к решению задачи

**Рефакторинг** - процесс улучшения структуры существующего кода без изменения его внешнего поведения. Основная цель рефакторинга — сделать код более понятным, поддерживаемым, гибким и пригодным для дальнейшего развития, при этом не добавляя новой функциональности и не исправляя ошибки (если они не связаны с плохой структурой 
кода).

### Типы паттернов
**Порождающие** паттерны - отвечают за создание объектов и обеспечивают гибкость в процессе инстанцирования. Они помогают сделать систему независимой от способа создания, композиции и представления объектов. Примеры:
- **Singleton** — гарантирует, что у класса есть только один экземпляр, и предоставляет глобальную точку доступа к нему
- **Factory Method** — определяет интерфейс для создания объекта, но позволяет подклассам изменять тип создаваемого объекта.
- **Abstract Factory** — предоставляет интерфейс для создания семейств связанных объектов без указания их конкретных классов.
- **Builder** — позволяет создавать сложные объекты пошагово
- **Prototype** — позволяет копировать объекты, не вдаваясь в подробности их реализации

**Структурные** паттерны - помогают организовать классы и объекты в более крупные структуры, сохраняя гибкость и *эффективность* системы. Примеры:
- **Adapter** — позволяет объектам с несовместимыми интерфейсами работать вместе.
- **Composite** — позволяет сгруппировать объекты в древовидные структуры и работать с ними как с единым объектом.
- **Proxy** — предоставляет суррогатный объект, который контролирует доступ к другому объекту.
- **Facade** — предоставляет простой интерфейс для сложной системы классов.
- **Decorator** — позволяет динамически добавлять объектам новую функциональность.

**Поведенческие** паттерны - отвечают за взаимодействие между объектами и распределение ответственности. Примеры:
- **Observer** — определяет зависимость "один ко многим" между объектами, чтобы при изменении состояния одного объекта все зависящие от него объекты уведомлялись автоматически.
- **Strategy** — позволяет выбирать алгоритм поведения во время выполнения программы.
- **Command** — инкапсулирует запрос как объект, позволяя параметризовать клиенты с различными запросами.
- **Iterator** — предоставляет способ последовательного доступа к элементам коллекции без раскрытия её внутренней структуры.
- **State** — позволяет объекту изменять своё поведение при изменении внутреннего состояния.

Также выделяются дополнительные типы паттернов:

**Архитектурные** паттерны (например, MVC, MVVM) — решают задачи на уровне архитектуры приложения.
Паттерны **параллельного программирования** (например, Active Object, Monitor Object) — помогают в работе с многопоточностью.

## Cirquit breaker ([опа](https://habr.com/ru/companies/otus/articles/778574/))
Работает как пробки в электросчётчике. Когда происходит перегрузка, он "выбивается", предотвращая возможные повреждения. Он мониторит вызовы к внешнему сервису и при обнаружении слишком большого количества неудачных попыток временно "отключает" вызов, предотвращая тем самым падение всей системы.

Основывается на трех основных состояниях:
- закрытое: запросы к сервису выполняются нормально
- открытое: включается при учащении сбоев, блокирует все вызовы
- полуоткрытое: включается из открытого состояния спустя некоторое время. Некоторые вызовы тестируются, чтобы проверить, исправился ли сбой

Полезные особенности:
- Инкапсулирует проблемы в одном сервисе, не затрагивая другие
- Позволяет регулировать поток запросов к сервисам (при микросервисной архитектуре разные сервисы испытывают разную нагрузку)
- Может быть интегрирован с системами мониторинга (отправлять отчёты, поднимать тревогу, ...)

## Event Sourcing
Паттерн, при котором состояние объекта определяется последовательностью событий, создающих, изменяющих и удаляющих объект

Простейшая реализация - две таблицы: первая с первичными ключами (представляет существующие объекты), вторая с событиями, связанными с этими первичными ключами (хранит **полный** лог изменений в системе)

## CQRS ([опа](https://habr.com/ru/companies/simbirsoft/articles/329970/))
Паттерн, при котором код, изменяющий состояние , отделяется от кода, читающего состояние: методы могут быть либо запросом, либо командой
- **Запрос** возвращает значение состояния и не меняет его
- **Команда** изменяет состояние, но не возвращает значение (*обычно* работает с конечным списком первичных ключей вместо условий `WHERE` (чтобы не дай бог не поменять то, что было добавлено/изменено другой командой после отправки команды))

Традиционно применяется в связке с паттерном Event sourcing: есть очередь команд и БД для чтения состояния. Команды из очереди выполняются по одной специальными обработчиками

## API Gateway
Паттерн, заключающийся в реализации фасада над несколькими сервисами и их API. Для конечноего пользователя API представляется единообразным, что бы за шлюзом не находилось.
API-шлюз выступает в качестве центральной точки входа для внешних запросов и обеспечивает единый интерфейс для доступа к различным его компонентам. Он решает такие задачи, как **маршрутизация запросов**, **аутентификация**, **авторизация**, **ограничение частоты запросов** и **сбор аналитических данных** API. Снимая с индивидуальных компонентов эти заботы, API-шлюз упрощает разработку, повышает производительность и общую безопасность приложения

## Saga ([опа](https://microservices.io/patterns/data/saga.html))
Паттерн, решающий проблему транзакций, затрагивающих несколько сервисов (у каждого из которых своя бд, *помним, да*)
Собственно сага - это последовательность локальных транзакций. Если транзакция падает с ошибкой, запускается серия компенсирующих транзакций (rollback, но не тупой, как в БД, а сильно более сложное действие (*как минимум потому, что за время между началом саги и ошибкой состояние могло кучу раз поменяться*)), возвращающих состояние к исходному

>[!tip] Под [статьёй](https://habr.com/ru/companies/otus/articles/751134/) на хабре пишут, что
>Компенсирующие транзакции должны быть идемпотентными (не менять стороннее состояние), т.е. если с ошибкой падает компенсирующая транзакция, мы можем этим пренебречь и повторять попытку, пока не получится

Есть два подхода:
- **Хореография** - каждая локальная транзакция создаёт и отправляет события, которые триггерят локальные транзакции в других сервисах
- **Оркестрация** - специальный объект-оркестратор определяет, какому сервису выполнять какие транзакции

## ... Driven Development ([опа](https://habr.com/ru/articles/459620/))
### Test...
ТЗ описывается через тесты. Сначала пишутся тесты, затем код, который эти тесты проходит. Уменьшает избыточность: если код проходит все тесты, дополнять его уже не нужно. Упрощает внесение изменений: если в процессе что-то ломается, автотесты тут же это покажут

### Type...
Спецификацией программы являются типы данных и сигнатуры
>[!note] Каво?
>Типы представляют из себя небольшие контрольные точки, благодаря которым мы получаем множество мини-тестов по всему нашему приложению. Причём затраты на создание типов минимальны и актуализировать их не требуется, так как они являются частью кодовой базы
>
>Из минусов только возрастающая сложность у языков с динамической типизацией. К примеру, для JavaScript этот подход тяжелее применить, чем для TypeScript

### Behavior...
Похоже на TDD, но TDD — это больше о программировании и тестировании на уровне технической реализации продукта, когда тесты создают сами разработчики. **BDD предполагает описание тестировщиком или аналитиком пользовательских сценариев на естественном языке**
>[!tip] Определение
>BDD — behaviour-driven development — это разработка, основанная на описании поведения. Определенный человек (или люди) пишет описания вида "я как пользователь хочу когда нажали кнопку пуск тогда показывалось меню как на картинке" (там есть специально выделенные ключевые слова). Программисты давно написали специальные тулы, которые подобные описания переводят в тесты (иногда совсем прозрачно для программиста). А дальше классическая разработка с тестами.

Преимущества:
- Тесты читаемые для не программистов.
- Их легко изменять. Они часто пишутся почти на чистом английском.
- Их может писать product owner или другие заинтересованные лица.
- Результаты выполнения тестов более "человечные".
- Тесты не зависят от целевого языка программирования. Миграция на другой язык сильно упрощается.

Недостатки: долго и дорого

### Feature...
*В статье многабукаф, лучше там почитать подробнее*
Основной целью данной методологии является разработка реального, работающего программного обеспечения систематически, в поставленные сроки (то есть максимальное количество рабочих фич в минимальное (ну, или адекватное, кому как) время)
Как и остальные адаптивные методологии, она делает основной упор на коротких итерациях, каждая из которых служит для проработки определенной части функциональности системы (итерации по 2 недели). Опрелелены 5 процессов:
- разработка общей модели; (начало проекта)
- составление списка требуемых свойств системы; (начало проекта)
- планирование работы над каждым свойством; (начало проекта)
- проектирование каждого свойства;
- конструирование каждого свойства.

Преимущества
- документация по свойствам системы;
- тщательное проектирование;
- проще оценивать небольшие задачи;
- тесты ориентированы на бизнес-задачи;
- проработанный процесс создания продукта;
- короткие итеративные циклы разработки позволяют быстрее наращивать функциональность и уменьшить количество ошибок.

Недостатки: слабая эффективность на маленьких проектах; значительные затраты на внедрение и обучение

### Model...
>[!tip] Определение
>**Разработка, управляемая моделями**, (англ. model-driven development) — это стиль разработки программного обеспечения, когда модели становятся основными артефактами разработки, из которых генерируется код и другие артефакты.

Проще говоря, суть разработки сводится к построению необходимых диаграмм, из которых впоследствии мы генерируем рабочий код проекта
Основная цель MDD — минимизация затрат, связанных с привязкой к конкретным системным платформам и программным инфраструктурам
Итерации:
- cначала разрабатывается модель предметной области проектируемого приложения, полностью независимая от имплементирующей технологии;
- затем она трансформируется специальным инструментом в платформо-зависимую модель;
- наконец, она переводится в исходный код на соответствующем языке программирования.
Преимущества:
- ускоряется вывод минимального жизнеспособного продукта (Minimum Viable Product) на рынок;
- сокращается время на генерацию каркаса приложения, модели классов, базы данных;
- постоянно обновляемая документация;
- для участников проекта диаграммы намного нагляднее кода.
Недостатки:
- для внедрение MDD потребуется использовать специальные программные решения, такие как Rational Software Architect, Simulink или Sirius;
- от программистов требуются внушительные знания проектирования диаграмм;
- значительные финансовые затраты на интеграцию данной методологии.

### Panic... (больше на издёвку похоже, чем на методологию, если честно)
Принципы:
- новые задачи важнее старых: новые фичи для клиента превыше всего
- "пишите столько кода, сколько нужно, чтобы решить проблему" (*я бы переформулировал как "семь бед - один ответ: костыль и велосипед"*): обсуждение дизайна и пользовательского опыта только замедляет разработку. Если что-то ломается, сначала нужно написать своё решение. Если оно работает, то проблема решена
- тесты должны писаться в самом конце: без комментариев
- доверять инстинкту: *программирование - это искусство, а программист - творец. Только смелым улыбается удача*
- процесс должен быть гибким: ничто не высечено в камне. Если бизнес хочет фичу в срок - процесс нужно нещадно гнуть
- управление должно быть полностью отдано менеджерам: рефакторинг может быть отложен по требованию бизнеса. Инженеры могут что-то вякать, но обязаны подчиняться приказам сверху

Плюсы: быстро, дёшево, сердито. Бизнес рад, потому что отчёты красивые, и новые фичи делаются в срок
Минусы: во всей красе проявятся спустя пару месяцев/лет, когда накопится техдолг, нужно будет рефакторить, добавлять новые фичи уже другим людям.

### Domain Driven Design
DDD — это набор правил, которые позволяют принимать правильные проектные решения. Данный подход позволяет значительно ускорить процесс проектирования программного обеспечения в незнакомой предметной области
>[!tip] Определение
>**Предметно-ориентированное проектирование** (реже проблемно-ориентированное, англ. Domain-driven design, DDD) — это набор принципов и схем, направленных на создание оптимальных систем объектов. Процесс разработки сводится к созданию программных абстракций, которые называются моделями предметных областей. В эти модели входит бизнес-логика, устанавливающая связь между реальными условиями области применения продукта и кодом.

Подход DDD особо полезен в ситуациях, когда разработчик не является специалистом в области разрабатываемого продукта, но при правильном понимании структуры может спроектировать приложение
Основная цель — это борьба со сложностью бизнес-процессов, их автоматизации и реализации в коде
Понятия:
- **единый язык**: Все участники общаются на нём, всё обсуждение происходит в терминах единого языка, и все артефакты максимально должны излагаться в терминах единого языка, то есть, начиная от ТЗ, и, заканчивая кодом
- **доменная модель** - словарь терминов из единого языка. И доменная модель, и язык ограничены контекстом (**bounded context**). Он ограничивает доменную модель таким образом, чтобы все понятия внутри него были однозначными, и все понимали, о чём идёт речь.
DDD не про архитектуру, а про язык и общение

Преимущества:
- почти все участники команды могут читать код проекта;
- постановка задач становится более явной;
- баги бизнес логики становиться проще искать;
- QA специалистам намного легче просматривать код и находить логические ошибки и баги.

Недостатки: высокая требуемая квалификация разработчиков, дорого, потому что учиться работать по DDD нужно будет вообще всем участникам

### Distributed Transactions in Microservices
**Scenario**: A fintech system processes payments across 10 microservices (e.g., fraud checks, inventory, notifications). A payment must roll back globally if any service fails.
**Question**: How would you ensure ACID-like guarantees without tight coupling? Discuss patterns (Saga, compensating transactions) and trade-offs (latency vs. consistency). What happens if a compensating transaction fails? 

To address distributed transactions in a microservices fintech system while preserving loose coupling and ACID-like guarantees, we use the Saga pattern with compensating transactions. Here's a structured approach:

#### 1. Pattern Selection: Orchestrated Sagas
For a payment system involving 10 services, orchestration (using a central coordinator) is preferable over choreography for:
- Explicit workflow control: Critical for financial systems to enforce auditability and compliance.
- Simplified error handling: The orchestrator tracks the transaction state and triggers rollbacks programmatically.

Reduced coupling: Services expose idempotent API endpoints (e.g., POST /reserve-funds) but remain unaware of the broader transaction context.

Example Flow:
1. Orchestrator starts a "Process Payment" saga.
2. Sequentially invokes services: Fraud Check → Inventory Reserve → Notify User → etc.
3. If any service fails (e.g., inventory shortage), the orchestrator executes compensating actions in reverse order.

#### 2. Compensating Transactions
Each service implements a compensating operation to undo its previous action:
- Idempotency: Compensations must handle retries (e.g., DELETE /reservation/{idempotency-key}).
- Atomicity per Service: Local ACID transactions ensure a service’s main action and compensation are atomic (e.g., reserve_funds and release_funds in the same database transaction).

Example Compensations:
- Fraud Check: No compensation needed (read-only operation).
- Inventory: ReleaseReservation(order_id).
- Payment Service: Refund(payment_id).

#### 3. Trade-offs: Consistency vs. Latency
Eventual Consistency: Sagas sacrifice strong consistency for availability. For example, a user might briefly see a refund as "pending" before it finalizes.

Latency: Orchestration adds minimal overhead compared to choreography (no event-bus delays), but retries for compensations increase end-to-end latency.

#### 4. Handling Failed Compensations
If a compensating transaction fails (e.g., the inventory service is down during rollback):
- Retry with Backoff: Use exponential retries (e.g., 1s, 5s, 15s) with idempotency keys.
- Dead Letter Queue (DLQ): After retries, log the failed compensation in a DLQ for manual intervention.
- Alerting: Trigger alerts to operations teams to resolve stuck transactions.
- Fallback State: Design services to tolerate temporary inconsistencies (e.g., flagging reservations as "stale" after a TTL).

#### 5. Complementary Patterns
**Idempotency Keys**: All API endpoints (including compensations) require idempotency keys to handle duplicate requests.
**Event Sourcing**: Log all saga steps as events for audit trails and recovery (e.g., replaying events if the orchestrator crashes).
**Circuit Breakers**: Prevent cascading failures by halting requests to unhealthy services during retries.

#### 6. Failure Scenario Example
Scenario:
1. Payment succeeds, but the notification service fails, triggering a rollback. The inventory compensation also fails due to a network partition.
2. Orchestrator retries ReleaseReservation 3 times with backoff.
3. After failures, the orchestrator writes the event to a DLQ and alerts engineers.
4. Engineers manually resolve the inventory reservation using logged data.
5. System design ensures no double-charging (idempotent refunds) despite temporary inconsistency.

#### Conclusion
By using orchestrated Sagas with retryable/idempotent compensations, we balance loose coupling with reliability. While eventual consistency is unavoidable, the trade-off is justified in high-throughput fintech systems where tight coupling (e.g., distributed locks) would harm scalability. Failed compensations are mitigated through retries, DLQs, and operational safeguards.

### Event-Driven Architecture for Real-Time Analytics
**Scenario**: You are tasked with building a real-time analytics platform that processes user interactions on a website.

To address the requirements of a real-time analytics platform for user interactions, an event-driven architecture (EDA) is often superior to a traditional request-response model in scenarios demanding high throughput, scalability, and low-latency processing. Below is a structured analysis of the decision criteria, benefits, challenges, and solutions:

6. When to Choose Event-Driven Architecture Over Request-Response
High Volume/Throughput: User interactions (e.g., clicks, page views) generate a massive stream of events. EDA decouples producers (website) and consumers (analytics processors), enabling asynchronous, parallel processing.

Real-Time Requirements: Immediate processing of events (e.g., live dashboards, fraud detection) requires non-blocking, event-triggered workflows.

Loose Coupling: Adding new analytics features (e.g., A/B test tracking) without disrupting existing components.

Scalability: Horizontal scaling of consumers to handle fluctuating workloads (e.g., traffic spikes during promotions).

Example: A request-response model would bottleneck at scale (e.g., synchronous API calls for each click), while EDA allows buffering and parallel processing via a message broker like Kafka or RabbitMQ.

7. Benefits of Event-Driven Architecture
Scalability: Dynamically add consumers to match event ingestion rates.

Fault Tolerance: Events persist in a broker (e.g., Kafka) during outages, reducing data loss.

Extensibility: New consumers (e.g., for ML model training) subscribe to the same event stream without code changes.

Low Latency: Process events in real time vs. batch processing.

8. Key Challenges and Mitigations
a. Event Ordering
Problem: User sessions require ordered processing (e.g., "add to cart" before "checkout").

Solution:

Use partitioned logs (e.g., Kafka) with a partition key (e.g., user_id or session_id) to ensure events for the same entity are ordered.

Trade-off: Global ordering is sacrificed for per-partition ordering, which suffices for most analytics use cases.

b. Idempotency
Problem: Duplicate events (e.g., due to network retries) skew analytics (e.g., double-counting page views).

Solution:

Idempotent Consumers: Track processed event IDs (e.g., UUIDs) in a cache (Redis) or database to deduplicate.

Idempotent Operations: Design aggregations (e.g., incrementing counters) to be naturally idempotent.

c. Data Loss
Problem: Broker failures or misconfigurations may drop unprocessed events.

Solution:

Durable Storage: Use brokers with disk persistence (e.g., Kafka with replication factor ≥3).

Acknowledgment Mechanisms: Consumers commit offsets only after successfully processing events (at-least-once delivery).

Dead Letter Queues (DLQ): Route failed events to a DLQ for reprocessing.

d. Backpressure Handling
Problem: Consumers overwhelmed by event influx cause delays or crashes.

Solution:

Pull-Based Consumption: Consumers fetch events at their own pace (e.g., Kafka consumers).

Autoscaling: Scale consumer instances based on lag metrics (e.g., Kafka consumer lag).

Rate Limiting: Throttle producers during overload (e.g., via API gateways) or prioritize critical events.

Buffering: Use brokers with high retention periods to absorb temporary spikes.

9. Complementary Patterns and Tools
Exactly-Once Semantics: Combine idempotent consumers with transactional outbox patterns or Kafka’s transactional API.

Schema Registry: Enforce event schema compatibility (e.g., Apache Avro) to prevent data corruption.

Circuit Breakers: Prevent cascading failures by isolating slow consumers.

Observability: Monitor event throughput, consumer lag (e.g., Prometheus/Grafana), and deduplication rates.

10. Trade-offs and Considerations
Eventual Consistency: Analytics may temporarily reflect stale data (e.g., delayed processing during backpressure).

Complexity: EDA introduces operational overhead (managing brokers, partitions, consumer groups).

Cost: Persistent brokers and scaling consumers increase infrastructure costs.

11. Failure Scenario Example
Scenario: A traffic spike overwhelms consumers, causing backpressure.

Autoscaling triggers new consumer instances to reduce lag.

Rate Limiting is applied to non-critical event producers (e.g., ad impressions) to prioritize core metrics (e.g., purchases).

DLQ captures malformed events for offline analysis without blocking the main pipeline.

Idempotent Counters ensure duplicates from retries do not corrupt results.

Conclusion
An event-driven architecture is ideal for real-time analytics platforms due to its scalability, fault tolerance, and ability to handle asynchronous workflows. While challenges like ordering, idempotency, and backpressure require careful design, tools like Kafka (for ordered, partitioned logs) and patterns like idempotent processing mitigate these risks. The trade-offs in complexity and eventual consistency are justified for real-time systems where latency and throughput are critical.

### Resilience and Fault Tolerance in Microservices
**Scenario**: A critical service in your microservices architecture is experiencing intermittent failures.
**Question**: How would you design the system to be resilient? Discuss the use of circuit breakers, retries, and fallback mechanisms. What strategies would you implement to prevent cascading failures across services?

To design a resilient microservices architecture and prevent cascading failures during intermittent critical service outages, we employ a combination of patterns, infrastructure strategies, and trade-offs. Below is a structured approach:

#### Core Resilience Patterns
- Circuit Breakers
     - Purpose: Prevent overwhelming a failing service by blocking requests after a failure threshold.
     - Implementation:
          - States:
               - Closed: Requests flow normally.
               - Open: Requests are blocked for a cooldown period (e.g., 30 seconds).
               - Half-Open: Allow limited requests to test recovery.
     
          - Tools: Use libraries like Resilience4j or integrate with service meshes (e.g., Istio).
     - Example: After 5 failures in 10 seconds, trip the circuit and return a 503 Service Unavailable for 30 seconds.
-  Retries with Backoff and Jitter
     - Purpose: Handle transient errors (e.g., network blips) without exacerbating failures.
     - Implementation:
          - Exponential Backoff: Wait 2^n * base_delay (e.g., 1s, 2s, 4s).
          - Jitter: Add randomness (e.g., ±0.5s) to avoid retry storms.
          - Idempotency: Ensure retries are safe (e.g., use unique idempotency_key for payments).
     - Trade-off: Limit retries (e.g., 3 attempts) to avoid prolonged latency.
-  Fallback Mechanisms
     - Purpose: Provide degraded functionality when a service is unavailable.
     - Strategies:
          - Cached Data: Serve stale but usable data (e.g., last-known inventory count).
          - Default Response: Return a generic response (e.g., "Recommendations unavailable; try popular items").
          - Circuit-Breaker Fallback: Return a static response (e.g., "Service temporarily down") when the circuit is open.

#### Preventing Cascading Failures
- Bulkheads
     - Purpose: Isolate failures by partitioning resources.
     - Implementation:
          - Thread Pools: Assign dedicated threads per service (e.g., via Java’s HystrixThreadPool).
          - Connection Pools: Limit database/HTTP connections per service.
     - Example: A failing payment service won’t exhaust threads needed for product catalog requests.
- Timeouts
     - Purpose: Fail fast to free resources.
     - Implementation: Set aggressive timeouts (e.g., 2s for HTTP calls) aligned with SLA requirements.
     - Trade-off: Risk of premature failures; balance with retry logic.
- Rate Limiting and Throttling
     - Purpose: Prevent overload during traffic spikes.
     - Tools: Enforce limits via API gateways (e.g., Kong, Envoy) or middleware (e.g., Redis Token Bucket).
     - Example: Allow 100 requests/sec per user during peak sales.
- Load Shedding
     - Purpose: Prioritize critical traffic during overload.
     - Strategies:
          - Prioritization: Drop non-critical requests (e.g., analytics events) first.
          - HTTP 429 Responses: Signal clients to retry later.

#### Infrastructure and Observability
- Health Checks and Load Balancing
     - Liveness Probes: Restart unhealthy pods (Kubernetes) or instances.
     - Readiness Probes: Remove instances from load balancers during degradation.
     - Example: AWS ELB automatically routes traffic away from failing EC2 instances.
- Service Mesh (e.g., Istio, Linkerd)
     - Benefits:
          - Centralized resilience policies (retries, timeouts, circuit breakers).
          - Metrics and tracing for cross-service observability.
     - Example: Istio’s VirtualService enforces retries and timeouts across all payment service calls.
- Observability
     - Metrics: Track error rates, latency, and circuit-breaker states (Prometheus/Grafana).
     - Distributed Tracing: Identify bottlenecks with Jaeger or Zipkin.
     - Logging: Correlate failures using structured logs (e.g., trace_id).

#### Handling Edge Cases and Failures
- Fallback Failure mitigation:
     - Layered Fallbacks: Primary fallback (cached data) → Secondary fallback (static response).
     - Graceful Degradation: Disable non-essential features (e.g., product reviews).
     - Example: If both the payment service and its fallback fail, redirect users to a "Try again later" page.
- Retry Storms mitigation:
     - Dead Letter Queues (DLQ): Move repeatedly failed requests to a DLQ for offline processing.
     - Alerting: Notify engineers when retry rates exceed thresholds.
- Data Consistency:
     - Saga Pattern: Use compensating transactions for distributed workflows (e.g., cancel an order if payment fails).
     - CRDTs: Resolve conflicts in eventually consistent systems (e.g., shopping cart merges).

#### Testing and Validation
- Chaos Engineering
     - Tools: Gremlin, Chaos Monkey.
     - Scenarios: Simulate service outages, latency spikes, or resource exhaustion.
     - Example: Randomly terminate Kubernetes pods to test auto-recovery.
- Load Testing
     - Tools: Gatling, Locust.
     - Goal: Validate auto-scaling and bulkhead effectiveness under peak traffic.

#### Trade-offs and Considerations
- Availability vs. Consistency: During outages, prioritize availability (AP from CAP) with eventual consistency.
- Latency vs. Safety: Aggressive timeouts improve latency but risk false failures.
- Complexity vs. Resilience: Service meshes add overhead but standardize fault tolerance.

#### Example Scenario
- Problem: Payment service fails intermittently during a flash sale.
- Circuit Breaker: Trips after 5 failures, blocking further requests for 30 seconds.
- Fallback: Returns cached payment options (e.g., saved credit cards) or defers to a "Pay Later" option.
- Bulkheads: Ensure failure doesn’t block cart or inventory services.
- DLQ: Failed payment requests are queued for reprocessing post-recovery.
- Alerting: Engineers receive a PagerDuty alert to investigate the root cause.

#### Conclusion
Resilience in microservices requires a layered approach: circuit breakers to isolate failures, intelligent retries to handle transient issues, and fallbacks to maintain partial functionality. Bulkheads, timeouts, and rate limiting prevent cascading failures, while observability tools provide visibility into system health. Trade-offs between latency, availability, and consistency are inevitable but manageable through thoughtful design. Regular chaos testing ensures the system withstands real-world failures, and a service mesh can streamline resilience implementation across large-scale architectures.

### CAP Theorem Trade-offs
**Scenario**: You are designing a distributed database for a social media application.
**Question**: How would you apply the CAP theorem in your design? Discuss the trade-offs between consistency, availability, and partition tolerance. Provide a scenario where you would prioritize one over the others and justify your choice.

The CAP theorem states that a distributed system can guarantee only two of three properties simultaneously: Consistency (all nodes see the same data), Availability (every request receives a response), and Partition Tolerance (the system operates despite network failures). In practice, partition tolerance (P) is non-negotiable for distributed databases, as network partitions are inevitable. This forces a trade-off between Consistency (C) and Availability (A) during partitions. Below is how this applies to a social media application:

CAP Trade-offs and Design Choices

| Property                | Implications for Social Media                                                                                                                                         |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Consistency (C)         | Ensures all users see the same data simultaneously (e.g., likes, comments). Requires locking or consensus protocols (e.g., Paxos, Raft), which may introduce latency. |
| Availability (A)        | Prioritizes uptime, allowing users to read/write even during partitions. Data may be stale or conflicting (e.g., a post appearing on some feeds but not others).      |
| Partition Tolerance (P) | Mandatory for global scalability. Social media apps must handle regional outages or network splits.                                                                   |

Example Database Choices:
- AP Systems (e.g., Cassandra, DynamoDB): Favor availability. Users can post/view content even during partitions, but may see inconsistencies (e.g., delayed likes).
- CP Systems (e.g., MongoDB, CockroachDB): Prioritize consistency. During partitions, writes/reads may fail to avoid data divergence (e.g., ensuring a deleted post disappears everywhere immediately).

Scenario: Prioritizing Availability (AP) for News Feed Functionality. Context: A social media news feed is read-heavy and requires low-latency global access. Users tolerate slight delays in consistency (e.g., seeing a post a few seconds late) but expect uninterrupted access.
Design Choice:
- AP Database (e.g., Apache Cassandra):
- Availability: Users can post and view feeds even during network splits.
- Eventual Consistency: Conflicts are resolved asynchronously (e.g., using timestamps or vector clocks).
- Partition Tolerance: Data is replicated across regions to survive outages.

Mitigating Consistency Risks:
- Conflict-Free Replicated Data Types (CRDTs): Resolve conflicts in likes/comments without central coordination.
- Sticky Sessions: Route users to the same region temporarily to reduce inconsistency.
- Client-Side Handling: Display a "posting..." indicator while synchronizing data in the background.

Scenario: Prioritizing Consistency (CP) for Direct Messaging. Context: Direct messages (DMs) require strict consistency to ensure messages are delivered in order and not duplicated/lost.
Design Choice:
- CP Database (e.g., CockroachDB):
- Consistency: Use distributed transactions (e.g., Two-Phase Commit) to guarantee atomicity.
- Partition Tolerance: Failover to a majority partition during network splits; minority partitions reject writes.

Mitigating Availability Risks:
- Retry Mechanisms: Clients automatically retry failed messages.
- Caching: Temporarily store undelivered messages locally until the system recovers.

**Why Prioritize AP for Most Social Media Features?**
- User Experience: Social media thrives on engagement. Downtime or write rejections during partitions frustrate users.
- Scale: AP systems handle global traffic spikes more efficiently (e.g., viral posts).
- Asynchronous Workflows: Many features (e.g., notifications, feeds) tolerate eventual consistency.

Pitfalls and Mitigations

| Pitfall                                | Mitigation                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------------- |
| Stale Reads                            | Use client-side caching with TTLs and versioned data.                             |
| Write Conflicts                        | Implement CRDTs or application-layer conflict resolution (e.g., last-write-wins). |
| Temporary Unavailability in CP Systems | Deploy read replicas in CP databases for failover.                                |

Conclusion
For most social media use cases (e.g., posts, feeds), AP systems strike the best balance, prioritizing availability and partition tolerance while managing consistency trade-offs. However, CP systems are critical for features requiring strong guarantees (e.g., DMs, payments). The key is to decompose the application and apply CAP-aware databases per bounded context, rather than enforcing a one-size-fits-all approach. Always align CAP choices with business priorities: user engagement favors AP, while transactional integrity demands CP.

### Data Consistency in Microservices
**Scenario**: Your microservices architecture requires data consistency across multiple services.
**Question**: How would you achieve this? Discuss eventual consistency, data replication strategies, and the challenges of maintaining consistency in a distributed system. What patterns would you use to handle conflicts?

#### Consistency Models in Microservices
45. Strong Consistency vs. Eventual Consistency
- Strong Consistency guarantees that all clients see the same data at the same time, following any write operation. This model simplifies reasoning about system state but can severely limit scalability and availability, especially in geographically distributed systems.
- Eventual Consistency allows for temporary discrepancies between services' views of data, with the guarantee that, in the absence of new updates, all replicas will converge to the same state. This model aligns well with microservices' scalability and independence but introduces complexity in ensuring data convergence and handling intermediate inconsistencies.
- Given the distributed nature of microservices, eventual consistency is often the pragmatic choice, balancing consistency with availability and partition tolerance as per the CAP theorem.

#### Data Replication Strategies
Ensuring data consistency across microservices typically involves replicating data changes and propagating them to relevant services. Key strategies include:
- **Event-Driven Architecture (EDA)**
     - Utilizing an event-driven approach, services emit events when their data changes. Other services subscribe to these events to update their own data stores accordingly.
     - Advantages:
          - Loose coupling between services.
          - Asynchronous communication enhances scalability and resilience.
     - Implementation:
          - Use message brokers (e.g., Kafka, RabbitMQ) to facilitate event distribution.
          - Employ event sourcing to capture all changes as a sequence of events, enabling services to reconstruct state.
- **Change Data Capture (CDC)**
     - CDC involves monitoring and capturing changes in a service's database and propagating these changes to other services.
     - Advantages:
          - Ensures that all data modifications are tracked and can be replicated accurately.
          - Minimizes the need for tight coupling between services.
     - Implementation:
          - Utilize tools like Debezium that integrate with databases to stream change events.
          - Incorporate a message broker to distribute change events to subscribing services.
- **API Composition and CQRS**
     - API Composition: Services query other services’ APIs to fetch the latest data when needed. This can ensure up-to-date information but may introduce latency and increased inter-service communication.
     - Command Query Responsibility Segregation (CQRS): Separates read and write operations, allowing services to maintain separate models optimized for each operation, often combined with event sourcing for consistency.

#### Challenges in Maintaining Consistency
Maintaining consistency in a distributed microservices architecture introduces several challenges:
- **Network Partitions and Failures**: Network issues can prevent services from communicating, leading to temporary inconsistencies or unavailability.
- **Latency**: Propagation delays in events or data replication can result in different services having different views of the data for a period.
- **Conflict Resolution**: Concurrent updates to the same data across multiple services can lead to conflicts that need resolution.
- **Transactional Boundaries**: Distributed transactions across services are complex and can undermine the benefits of microservices, such as autonomy and resilience.

#### Patterns for Handling Conflicts and Ensuring Consistency
To address these challenges, several patterns and strategies can be employed:
- Saga Pattern
     - The Saga pattern orchestrates a series of local transactions across services, ensuring consistency through compensating transactions in case of failures.
     - Types:
          - Choreography-Based Saga: Each service publishes and listens to events, triggering subsequent transactions without a central coordinator.
          - Orchestration-Based Saga: A central saga orchestrator manages the sequence of transactions and compensation actions.
     - Advantages:
          - Avoids distributed transactions, maintaining service autonomy.
          - Provides a clear flow of operations and compensations in case of failures.
- Outbox Pattern
     - The Outbox pattern ensures that messages (events) are reliably published by coupling state changes and event publication within the same transactional boundary.
     - Implementation:
          - When a service performs a state change, it also writes the corresponding event to an outbox table within the same database transaction.
          - A separate process reads from the outbox and publishes events to the message broker, ensuring atomicity between state changes and event publication.
          - Advantages: Guarantees that events are published exactly once, preventing data loss or duplication.
- Conflict-Free Replicated Data Types (CRDTs)
     - CRDTs are data structures designed for distributed systems that automatically resolve conflicts in a mathematically predictable manner.
     - Advantages:
          - Enable automatic conflict resolution without complex reconciliation logic.
          - Suitable for specific use cases where data can be modeled with CRDTs (e.g., counters, sets).
-  Versioning and Optimistic Concurrency Control
     - Using version numbers or timestamps to detect concurrent modifications, allowing services to handle conflicts gracefully.
     - Implementation:
          - Each data record includes a version identifier.
          - When updating data, the service checks that the version has not changed since it was read.
          - If a version mismatch is detected, the update is retried or a conflict resolution mechanism is triggered.
     - Idempotent Operations
          - Designing services to handle repeated operations without unintended side effects, ensuring that retries do not exacerbate inconsiderate states.
          - Advantages: Enhances resilience by allowing safe retries of operations in case of transient failures.
#### Best Practices for Maintaining Consistency
a. Design for Failure
Assume that failures will occur and design services to handle partial failures gracefully, maintaining overall system consistency through compensations and retries.

b. Decentralize Data Ownership
Each microservice should own its data, enforcing clear boundaries and preventing tight coupling, which aids in maintaining consistent state independently.

c. Use Idempotency Keys
Implement idempotency keys in API requests to prevent duplicate processing, especially in scenarios involving retries.

d. Monitor and Observe
Implement comprehensive monitoring and observability to detect inconsistencies early, enabling prompt resolution and system reliability.

e. Documentation and Contracts
Maintain clear documentation and service contracts to ensure that all services adhere to agreed-upon protocols for data exchange and consistency.

#### Core Design Patterns & Best Practices
**Scalability & Performance**
- Chunk-Based File Storage:
     - Split files into chunks (e.g., 4-16 MB) to enable parallel uploads, deduplication (via SHA-256 hashing), and resumable transfers.
     - Deduplication: Store chunks uniquely based on hash, reducing storage costs by 30-50% for common files.
- Geo-Distributed Storage: Use S3 Multi-Region Access Points or Google Cloud Storage with regional buckets to comply with data residency laws.
- Caching Layers: Redis for metadata caching (e.g., file permissions, recent activity) and CDN for static/immutable assets (e.g., images, videos).
- Stateless Services: Deploy upload/download services as stateless containers (e.g., Kubernetes pods) for horizontal scaling.
**Data Consistency & Syncing**
- Eventual Consistency Model:
     - Metadata updates (e.g., file renames) use DynamoDB streams + Lambda for async propagation.
     - Clients receive sync events via Kafka to reconcile local state.
- Conflict Resolution:
     - Last Writer Wins (LWW) for trivial conflicts (e.g., filename changes).
     - Manual Merge for documents (e.g., notify users when conflicting edits occur).
- Operational Transform (OT): Used in real-time collaboration to preserve document consistency (e.g., Google Docs).
**Security**
- Zero Trust Architecture:
     - Token-based auth with short-lived JWTs; mutual TLS between services.
     - Client-side encryption option for sensitive files (e.g., using WebCrypto API).
- Permission Model:
     - Hierarchical RBAC (e.g., owner > editor > viewer) with folder-level inheritance.
     - Pre-signed URLs with embedded access policies for shared links ([опа, ссылка](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)).
     - Audit Logging: All file operations logged to SIEM tools (e.g., Splunk) for compliance (GDPR, HIPAA).

#### Critical Workflows
