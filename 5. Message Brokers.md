# База
## Message Broker (Брокер сообщений)
**Архитектурный паттерн**, позволяющий получать сообщения из нескольких источников, определять путь к точке назначения и направлять сообщения по этому пути
1. Промежуточное программное обеспечение
2. Обеспечивает асинхронный обмен сообщениями между распределенными системами
3. Управляет очередями сообщений
4. Гарантирует доставку и маршрутизацию сообщений
5. Позволяет преобразовывать формат сообщений
## Message Queue (Очередь сообщений)
1. Буферное хранилище сообщений
2. Обеспечивает временное накопление сообщений
3. Поддерживает принцип FIFO (First In, First Out)
4. Позволяет системам обмениваться данными асинхронно
5. Помогает управлять нагрузкой
## Publisher (Издатель)
1. Компонент, отправляющий сообщения в брокер
2. Генерирует и публикует события
3. Не знает о конкретных получателях
4. Освобождается от ожидания обработки сообщения
## Consumer (Потребитель)
1. Компонент, получающий и обрабатывающий сообщения
2. Подписывается на определенные типы сообщений
3. Может быть несколько параллельных потребителей
4. Забирает сообщения из очереди
## Плюсы Message Brokers vs HTTP
1. Плюсы:
     1. Асинхронность коммуникаций
     2. Буферизация нагрузки
     3. Отказоустойчивость
     4. Масштабируемость
     5. Гарантированная доставка сообщений
     6. Декомпозиция систем
     7. Возможность retry механизмов
2. Минусы:
     1. Дополнительная сложность инфраструктуры
     2. Overhead на передачу сообщений
     3. Необходимость настройки и поддержки
     4. Потенциальная задержка доставки
     5. Сложность мониторинга
## Механизмы доставки

**Point-to-Point**
1. Отправитель отправляет сообщение, которое будет получено ровно одним потребителем
2. Традиционно реализуется при помощи очередей
3. Очереди в общем случае будут пытаться балансировать отправку сообщений между потребителями

**Pub-Sub**
1. Модель коммуникации "многие ко многим"
2. Традиционно реализуется при помощи топиков
3. Publisher отправляет сообщения в топик
4. Несколько Subscriber могут получать одно сообщение
5. Слабая связанность компонентов
6. Динамическая подписка/отписка
7. Горизонтальная масштабируемость
8. Схема работы: `Publisher -> Topic -> Subscribers(1,2,3...)`
## Push vs Pull в MQ
1. Push-based:
     1. Моментальная доставка
     2. Меньше задержки
     3. Меньше нагрузка на клиента
     4. Сложнее контролировать скорость
     5. Риск перегрузки получателя
2. Pull-based:
     1. Получатель сам определяет темп
     2. Легче масштабировать
     3. Больше контроля
     4. Возможные задержки
3. Способность сохранять сообщения
4. Защита от потери данных
5. Персистентность очередей
6. Восстановление после перезагрузки
7. Уровни:
     1. Временные очереди
     2. Постоянные очереди
     3. Персистентные очереди с репликацией

## Замена HTTP на Message Broker
1. Подходит для:
     1. Асинхронных операций
     2. Распределенных систем
     3. Слабосвязанных компонентов
     4. Очередей задач
2. Не подходит для:
     1. Синхронные вызовы

     4. Маленьких размер сообщения (запроса)
     5. Простые архитектуры

# Kafka
## Определение
**Kafka** - распределённая система потоковой обработки сообщений
1. Высокопроизводительный распределённый брокер сообщений
2. Opensource проект от Apache
3. Написан на Java и Scala
4. Используется для построения потоковых pipeline

`Publisher -> Topic -> Subscribers(1,2,3...)`

## Решаемые проблемы:
1. Большие объемы данных
2. Распределенная обработка событий
3. Асинхронное взаимодействие сервисов
4. Буферизация нагрузки
5. Сбор метрик и логирование
6. Интеграция разнородных систем

## Ключевые особенности:
1. Гарантии:
     1. Ordered commit
     2. Репликация сообщений
     3. Exactly-once processing
     4. Возможность replay событий
2. Преимущества:
     1. Горизонтальное масштабирование
     2. Высокая производительность
     3. Отказоустойчивость
     4. Персистентность
     5. Replay событий
     6. Поддержка stream processing
     7. Репликация данных
     8. Поддержка strict ordering
3. Области применения:
     1. Микросервисы
     2. Логирование
     3. Мониторинг
     4. Event Sourcing
     5. Streaming Analytics
     6. IoT платформы
4. Технические приколы
     1. Брокер более простой чем у других реализаций, часть функций (получение новых сообщений, например) переложена на клиента, что ускоряет работу
     2. Использует гибридный механизм доставки сообщений: топики используются и для Point-to-Point, и для Pub-Sub (в отличие от традиционных реализаций)
     3. Каждый топик имеет свой журнал, в который пишутся и из которого читаются сообщения. Применяются указатели, которые постоянно сдвигаются вперёд
     4. Для ускорения своей работы Kafka периодически чистит старые записи в журнале вне зависимости от того, прочитал клиент сообщение или нет. Клиент сам должен заботиться об этом
## Архитектура Kafka:
1. Компоненты:
     1. Producer (отправитель)
          1. Публикует сообщения в топики
          2. Может выбирать партицию
          3. Настраивает уровень надежности
     2. Consumer (получатель)
     3. Broker (сервер Kafka)
     4. Zookeeper (координация)
     5. Topic (логическая группа сообщений)
     6. Partition (физическое разделение топика)
2. Структура:

```
Cluster
├── Broker1 
│   ├── Topic1
│   │   ├── Partition0
│   │   └── Partition1
│   └── Topic2
│       ├── Partition0
│       └── Partition1
├── Broker2
└── Broker3
```

## Работа очередей
**Особенности**:
- Распределенная очередь
- Персистентное хранение
- Горизонтальная масштабируемость
- Репликация сообщений

**Процесс**:
1. Producer отправляет сообщение
2. Сообщение попадает в партицию топика
3. Сохраняется на диске
4. Consumer забирает сообщение
5. Отслеживается offset прочитанных сообщений

**Модели**:
- Point-to-Point
- Pub/Sub

**Механизмы**:
- **Consumer Groups**
     - Именованный указатель, контролируемый потребителем
     - Указывает на смещение сообщения в partition'е
     - Несколько потребителей (экземпляров и потоков) могут использовать один и тот же указатель
     - Несколько указателей могут указывать на один топик
- Topic подписки
- Распределённая обработка

**Consumer Group** - множество консюмеров, подключившихся к одному топику (*под одним `group_id`*). Каждый из них получает своё подмножество партиций, таким образом два консюмера не могут прочитать одно и то же сообщение. **Нужно для повышения пропускной способности одного топика**

**Консюмеры и группы консюмеров (Consumer Groups)**
1. Подключается к топику со своим `group_id`
2. Получает от брокера партицию для потребления и смещение в этой партиции (получаемое смещение конфигурируется на клиенте: получить указатель на самое новое или самое старое сообщение)
3. Потребитель запрашивает сообщения из топика, что выливается в чтение их из лога ![image](Static/5.kafka-consumers-1.png)
4. Новое смещение регулярно отправляется брокеру и фиксируется во внутреннем топике `__consumer_offsets`
5. Считанные сообщения никак не удаляются (==что противоречит вышеупомянутому удалению старых сообщений для ускорения работы брокера, но мб имеется в виду, что другие реализации брокеров удаляют сообщения, как только консюмер их считывает==), что позволяет клиенту считывать сообщения повторно
6. Когда подключается второй логический консюмер со своим `group_id`, он получает свой собственный указатель ![image](Static/5.kafka-consumers-2.png)
7. Таким образом, топик в Kafka ведёт себя и как очередь, которую считывает один консюмер, и как топик для механизма подписки и публикации с несколькими подписанными консюмерами с тем преимуществом, что сообщения хранятся долговременно и могут быть прочитаны несколько раз

**Консюмеры внутри группы консюмеров**
1. Когда один-единственный консюмер читает из партиции, он имеет *абсолютную власть* над указателем и читает сообщения как описано выше
2. Если к топику **с одной партицией** подключаются несколько консюмеров **под одним** `group_id`,  последний подключившийся получит контроль над указателем (==какой именно контроль?==), и только он будет получать новые сообщения (==непонятно, каким образом: клиенты же сами ответственны за получение сообщений, что мешает первым консюмерам опрашивать топик?==) ![image](Static/5.kafka-consumers-3.png)
3. Обычно несколько консюмеров создаются для параллельной обработки сообщений. С Kafka есть два основных подхода к увеличению пропускной способности (раз уж из одной партиции может читать только один консюмер)
     1. Использовать параллелизм внутри самого консюмера (усложняет логику, утяжеляет консюмер)
     2. Использовать больше партиций (каноничный)

**Несколько партиций**
1. Если один консюмер подписывается на топик с двумя партициями, он получает контроль над двумя указателями и получает сообщения из обеих партиций ![image](Static/5.kafka-consumers-4.png)
2. Если к тому же топику под тем же `group_id` подключится ещё один консюмер, один из указателей будет передан от первого консюмера второму ![image](Static/5.kafka-consumers-5.png)

## Топики, партиции, сегменты
**Topic**
- Логическая группа сообщений
- Именованный канал
- Может иметь несколько партиций (горизонтальное масштабирование)

**Partition**
- Основной механизм для распараллеливания чтения сообщений
- Физическое хранилище сообщений
- Упорядоченная последовательность со строгими гарантиями
- Может реплицироваться
- Имеет уникальный offset
- Продюсер решает, в какую партицию отправить сообщение
- Типы (==писала гопота, гуглёж не выдал никаких типов партиций==):
     - Log-compacted партиции
          - Хранение только последних версий ключей
          - Удаление устаревших записей
     - Обычные партиции
          - Последовательное хранение всех сообщений
          - Retention by time/size
     - Транзакционные партиции
          - Поддержка атомарности операций
          - Exactly-once семантика

**Сегменты**
- Части партиции на диске
- Ограничены по размеру
- Позволяют эффективно хранить данные
- Поддерживают ротацию (вот [тут](https://gist.github.com/jeqo/d32cf07493ee61f3da58ac5e77b192b2) что-то написано об этом, но не понял, в чём заключается суть ротации)
- Периодически удаляются, если не поступает новых сообщений (первый ответ [здесь](https://stackoverflow.com/questions/41048041/kafka-deletes-segments-even-before-segment-size-is-reached))

## Система хранения данных
Kafka обеспечивает поддержку истории сообщений через фундаментальный принцип append-only log-структуры данных. Каждая партиция топика представляет собой упорядоченную последовательность сообщений, которые хранятся максимально эффективно и долго.

Механизм хранения основан на сегментированных файлах, где каждый сегмент содержит определенный диапазон сообщений. Сообщения не удаляются физически, а помечаются для удаления по истечении настроенного времени жизни или достижении максимального размера партиции.

Retention period по умолчанию составляет 7 дней, но может быть гибко настроен администратором кластера. Это позволяет потребителям возвращаться к историческим данным, восстанавливать состояние системы или выполнять репликацию с определенного момента.

Специальные индексные файлы обеспечивают быстрый поиск и доступ к конкретным сообщениям по offset, что критично для эффективного воспроизведения истории.

Пример конфигурации хранения
```retention_settings
configs = {
    'log.retention.hours': 168,  # 7 дней
    'log.segment.bytes': 1073741824,  # 1 ГБ
    'log.retention.check.interval.ms': 300000  # Проверка каждые 5 минут
}
```

Этапы:
1. Producer создает сообщение
2. Выбирает партицию (key/round-robin)

## Репликация
**Репликация** - это механизм создания копий партиций топиков на нескольких брокерах для обеспечения отказоустойчивости и высокой доступности данных.
- Один брокер в кластере обязан принять на себя роль **Контроллера**
- Он назначает роли *master* и *slave* для каждой партиции в каждом топике. Master ответственен за приём сообщений от продюсеров и отправку их консюмерам
- Все получаемые сообщения реплицируются на slaves. Каждая нода, содержащая логи данной партиции, называется репликой

Архитектура репликации
```
Leader Partition
│
├── Follower 1 (Replica)
├── Follower 2 (Replica)
└── Follower 3 (Replica)
```

**Синхронная vs Асинхронная репликация**:
- Синхронная:
     - Лидер ожидает подтверждения от всех реплик перед фиксацией записи
     - Высокая надежность, но более низкая производительность
     - Гарантирует консистентность данных
- Асинхронная:
     - Лидер не ожидает подтверждения от всех реплик
     - Высокая производительность
     - Риск потери данных при сбое

**Настройка репликации**:
- Определение фактора репликации (replication factor)
- Конфигурация в файле `server.properties`
- Настройка параметров `min.insync.replicas`
- Выбор стратегии подтверждения записи (acks)

Пример конфигурации:
```python
producer = KafkaProducer(
    # Синхронная репликация
    acks='all',  
    
    # Асинхронная репликация  
    acks=1
)
```

**Стратегии**:
- Репликация лидер-последователь (leader-follower)
- Один брокер - лидер партиции, остальные - реплики
- Автоматическая смена лидера при сбое (failover)
- Распределение реплик по разным стойкам/зонам доступности

**ISR** (In-Sync Replicas):
- Набор реплик, которые находятся в синхронизированном состоянии с лидером
- Содержит реплики, которые успели получить и зафиксировать последние записи
- Используется для обеспечения отказоустойчивости: если лидер падает, одна из таких реплик берёт управление на себя

**Параметры конфигурации ISR**:
- `replica.lag.time.max.ms` - максимальное время отставания реплики
- `min.insync.replicas` - минимальное количество синхронизированных реплик
- `default.replication.factor` - фактор репликации по умолчанию (количество реплик + 1 лидер)

Параметры настройки:
```python
# Настройки Producer
producer_config = {
    'bootstrap.servers': 'kafka1:9092,kafka2:9092',
    'acks': 'all',  # Синхронное подтверждение
    'min.insync.replicas': 2  # Минимум 2 синхронные реплики
}

# Настройки Kafka
kafka_config = {
    'replica.lag.time.max.ms': 10000,
    'default.replication.factor': 3
}
```

- all (-1): Подтверждение от всех реплик

![image](Static/5.kafka-acknowledgements.png)
**Зачем**
- Контроль надежности доставки
- Влияние на производительность
- Настройка отказоустойчивости

### Многостраничное чтение (multimaster replication) ==так и не понял, к чему это==
Многомастерная репликация в Kafka реализована через сложный распределенный протокол, который обеспечивает высокую доступность и отказоустойчивость данных.
Архитектура репликации базируется на модели "один лидер - множество последователей" (leader-follower). Каждая партиция топика имеет один узел-лидер, который принимает все записи, и несколько узлов-реплик, которые синхронизируют данные.
Ключевой компонент - контроллер кластера (Controller Node), который управляет распределением лидерства и отслеживает состояние всех узлов. При падении лидера происходит автоматический выбор нового лидера из пула синхронизированных реплик (ISR - In-Sync Replicas).
Репликационный протокол поддерживает несколько режимов синхронизации:
- Асинхронная репликация с минимальными задержками
- Синхронная репликация с гарантией записи на все реплики
- Настраиваемое количество реплик для записи
Механизмы обеспечения консистентности включают проверку минимального количества синхронизированных узлов и настройку уровней подтверждения (acknowledgement).

## Семантики доставки
**At Most Once**
- Максимальная производительность
- Возможна потеря сообщений
- Сообщение отправляется без гарантий доставки
```python
producer = KafkaProducer(
    acks=0,  # Без подтверждения
    retries=0
)
```

**At Least Once**
- Гарантия доставки сообщения
- Возможны дубликаты
- Повторные попытки отправки
```python
producer = KafkaProducer(
    acks='all',  # Полное подтверждение
    retries=3    # Повторные попытки
)
```

**Exactly Once**
- Идемпотентная доставка
- Исключение дубликатов
- Использует транзакционный API
```python
producer = KafkaProducer(
    enable_idempotence=True,
    transactional_id='unique_id'
)
```

| Семантика     | Надежность | Производительность | Дубликаты |
| ------------- | ---------- | ------------------ | --------- |
| At Most Once  | Низкая     | Высокая            | Нет       |
| At Least Once | Средняя    | Средняя            | Да        |
| Exactly Once  | Высокая    | Низкая             | Нет       |

# RabbitMQ
## Структура
Компоненты:
- **Producer** (отправитель сообщений)
- **Broker** (брокер сообщений)
- **Exchange** (обменник, роутер, использует **Binding** - правило, по которому осуществляется маршрутизация; отношение между обменником и очередью)
- **Queue** (очередь)
- **Consumer** (получатель сообщений)

`Producer → Exchange → Queue → Consumer`

>[!tip]
>Консюмеры, подписанные на одну очередь, получают сообщения в том порядке, в котором они подписывались на очередь.
>Порядок цикличен: если есть два консюмера, и чётные сообщения занимают много времени на обработку, а нечётные - мало, то кролик всё равно будет пихать сообщения консюмерам поровну.
>Его не волнует, обработал консюмер сообщение или нет - *honey, it's time to process another message - yes, dear*.
>В `aio-pika` это чинится установкой параметра канала [`prefetch_count=1`](https://www.rabbitmq.com/docs/consumer-prefetch) (на принимающей стороне, если что)

## Exchange Router types
**Direct**
- Точное совпадение routing key
- 1:1 маршрутизация
- Быстрая доставка

**Fanout**
- Рассылка всем подписчикам
- Широковещательная рассылка
- Игнорирует routing key

**Topic**
- Маршрутизация по шаблону
- Поддержка масок (`#`, `*`)
- Гибкая фильтрация

**Headers**
- Маршрутизация по заголовкам
- Сложная фильтрация
- Игнорирует routing key
- Используется аргумент `x-match` в обменнике

## Приоритеты сообщений
- Настройка в очереди
- Диапазон 1-255 (рекомендованы 1-5; из-за того, что приоритет логически - unsigned byte, значения могут быть 0-255)
     - Крайне не рекомендуется использовать много разных приоритетов, потому что под каждый из них выделяется своя подочередь, что жрёт память и процессор
- Влияние на порядок обработки: когда кролик решает, какое сообщение отправить в первую очередь, он выбирает сообщение с бОльшим приоритетом
     - *Если я правильно понял, то когда консюмер условно задаёт `prefetch=10`, и в очередь поступает 10 сообщений с разным приоритетом, они поступают консюмеру в том же порядке, в котором пришли в очередь, а приоритет начинает иметь значение тогда, когда сообщений в очереди больше, чем консюмер может принять за раз*
- Требует специальной конфигурации

```python
channel.queue_declare(
    queue='priority_queue', 
    arguments={
        'x-max-priority': 10
    }
)
```

## Аргументы (похоже, имеются в виду [`x-arguments`](https://www.rabbitmq.com/docs/queues#optional-arguments) очередей)
- тип очереди
- предельное количество *пере*доставок сообщений в quorum очереди (*redelivery limit*)
- максимальное количество приоритетов
- `x-message-ttl`: время жизни сообщения
- `x-expires`: время жизни очереди
- `x-max-length`: максимальная длина очереди
- `x-dead-letter-exchange`: DLX

## DLQ (Очередь мертвых сообщений) [дока](https://www.rabbitmq.com/docs/dlx)~~2~~
Мёртвое сообщение - это сообщение, для которого выполняется любое из условий:
- Сообщение было отфутболено:
     - получатель отказался обрабатывать сообщение (*исход* [`rejected`](https://docs.oasis-open.org/amqp/core/v1.0/os/amqp-core-messaging-v1.0-os.html#type-rejected): сообщение повреждено, неправильно отформатировано и не может быть обработано)
     - или консюмер отказался обрабатывать его при помощи `basic.reject` или `basic.nack` с параметром `requeue=false`
- Срок годности сообщения превысил настроенный TTL сообщения или очереди
- Очередь превысила свой лимит количества одновременно хранимых сообщений
- Сообщение возвращалось в очередь типа quorum больше раз, чем позволено (заголовок сообщения `x-delivery-count`, устанавливаемый очередью, и политика `delivery-limit`)
Механизм:
- Перенаправление проблемных сообщений
     - Можно настроить обменник, в который будут отправляться все мёртвые сообщения: политика `dead-letter-exchange` или аргумент очереди `x-dead-letter-exchange`
     - Если для очереди, в которой лежали мёртвые сообщения, был настроен *routing key* при помощи аргумента очереди `x-dead-letter-routing-key`, то сообщения отправляются в обменник с ним. В противном случае отправляются в обменник с теми ключами, с которыми они были изначально опубликованы.
     - Если очередь, в которую отправляются мёртвые сообщения, отправляет сообщения обратно без установки *ключа маршрутизации мёртвого сообщения* (что бы это ни значило), то образуется замкнутый круг, и кролик сам обрывает это безобразие, дропая сообщение
>[!note] Обратите внимание
>Если `x-dead-letter-routing-key` не настроен, то сообщение будет отправлено в обменник со **всеми** своими исходными ключами

- Обработка недоставленных сообщений
- Анализ ошибок
- Настройка политик

```python
channel.queue_declare(
    queue='main_queue',
    arguments={
        'x-dead-letter-exchange': 'dlx_exchange',
        'x-dead-letter-routing-key': 'error'
    }
)
```

## Сохранение данных
Принцип записи сообщений на диск:
- В общем случае сообщения записываются на диск с задержкой, во время которой сообщения остаются в оперативной памяти
- Небольшое (зависит от того, как быстро консюмеры потребляют сообщения) количество сообщений не удаляется из оперативной памяти, чтобы быстро передать их консюмерам
- Если поступившее сообщение немедленно принимается консюмером, и последний успевает подтвердить обработку (*acknowledgement*) сообщения до того, как оно было записано на диск, операция записи на диск отменяется (смысл записывать уже обработанное сообщение? Его уже удалять нужно)
У каждой ноды кролика есть своя папка для хранения сообщений из очередей и потоков, расположенных на данной ноде. Сообщения хранятся в подпапках данной папки, для каждого типа очереди своя подпапка:
- `msg_stores` для классических очередей
- `quorum` *угадай, для чего*
- `stream` *угадай, для чего*

## Типы очередей
- **Quorum**
     - Современные, надёжные, реплицируемые
     - Такие же, как классические, в следующих операциях:
          - чтение сообщений, регистрация консюмеров
          - подтверждение получения сообщения консюмером
          - отмена получения сообщения
          - чистка очереди (purge)
          - удаление очереди (delete)
     - Есть небольшие отличия от классических очередей в
          - объявлении очереди
          - установке `prefetch` для консюмеров (==что отличается?==)
- **Classic**
     - Предназначены для использования в случаях, где сохранность данных не является приоритетом, вследстве отсутствия репликации
     - По [сравнению](https://www.rabbitmq.com/docs/quorum-queues#feature-comparison) с quorum
          - ниже пропускная способность
          - выше задержка
- **Stream**
     - Структура данных, способная выполнять некоторые задачи аналогично очередям. Главная особенность - **скорость**
     - Моделирует лог, поддерживающий только запись в конец (несколько консюмеров могут читать одни и те же сообщения столько раз, сколько хотят). Сообщения хранятся в логе, пока не истечёт их срок годности (не уничтожаются при прочтении)
     - Призваны не заменить очереди, а дополнить их. Варианты использования:
          - **Огромные массовые рассылки** (если много консюмеров должны создать для себя отдельные очереди, то проще им всем читать из потока)
          - **Повторное чтение** (очереди уничтожают сообщения после прочтения. Потоки - нет)
          - **Хайлоад** (ни одна очередь не сравнится по пропускной способностью со специализированными системами логирования)
          - **Накопление большого количества сообщений** (очереди by design стремятся опустошить себя и проседают по производительности при большом количестве сообщений)

## Пакет `aio-pika`
### База
Сначала что в продюсере, что в консюмере создаётся **подключение** `connection = await connect("amqp://guest:guest@localhost/")`
Затем при помощи `async with connection:` создаётся **канал**: `channel = await connection.channel()`
На стороне консюмера можно указать, что консюмер должен отправить `ack` перед тем, как кролик отправит ему следующее сообщение из очереди (делается при помощи `await channel.set_qos(prefetch_count=1)`)
Необходимо **убедиться в том, что очередь существует** (в противном случае создать её) при помощи `queue = await channel.declare_queue('queue-name')`. Вызов функции идемпотентный: сколько раз не вызывай, будет ровно одна очередь
1. Если нужна временная очередь (например, пушить логи, ==хотя я не понял, почему бы не иметь конкретную очередь для этого, ну да ладно, пример-то про FANOUT был==), название очереди можно просто не передавать - оно будет сгенерировано случайно. Также можно указать параметр `declare_queue(exclusive=True)`, чтобы при отключении консюмера очередь удалялась
**Для отправки сообщения** нужно вызвать метод `publish` у обменника. Обменник можно получить при помощи свойства `channel.default_exchange` или `exchange = await channel.declare_exchange('exchange-name', ExchangeType.FANOUT)`
- `routing_key` определяет, по какому принципу получать сообщения консюмеру. Продюсер может указать вообще любой ключ от балды, и это будет проблема консюмера - указать нужный ключ, чтобы получить сообщение
**Для получения сообщения из нужного обменника** нужно его объявить так же, как в продюсере, и выполнить `await queue.bind(exchange)`, после чего можно подписываться на получение сообщений при помощи `await queue.consume(on_message_callback)`.
- При базовой маршрутизации (продюсер отправляет сообщения в очередь при помощи обменника по умолчанию (*он равен пустой строке, кстати*)) объявлять обменник и создавать привязку на стороне консюмера не нужно
- `on_message_callback` - это функция (как минимум в `aio-pika` она может быть как синхронной, так и асинхронной - под капотом всё равно она превращается во `Future`), которая будет вызываться при каждом получении сообщения. Если `prefetch_count` не определён, функция будет вызываться вне зависимости от того, закончилось ли выполнение предыдущего её вызова или нет
Для обеспечения бесконечной работы консюмера можно воспользоваться `await asyncio.Future()`
### **Для более гибкой настройки маршрутизации** нужно сделать следующее:
- Использовать Direct обменник (почти наверняка можно и нужно и Topic/Headers), потому что Fanout игнорирует `routing_key`
- На стороне продюсера использовать динамический `routing_key` в параметрах `exchange.publish()`
- На стороне консюмера можно подписаться на несколько ключей маршрутизации при помощи нескольких вызовов `await queue.bind(echange, routing_key='some-key')`
- Для обработки сообщений с разными `routing_key` можно использовать `queue.iterator()` и `message.process()`:

```python
async with queue.iterator() as iterator:  
    message: AbstractIncomingMessage  
    async for message in iterator:  
        async with message.process():  
            print(f" [x] {message.routing_key!r}:{message.body!r}")
```

1. Объявить обменник с типом `ExchangeType.TOPIC`. Всё.
2. Для маршрутизации используются ключи, состоящие из слов, разделённых точками. Длина ключа не может быть больше 255 символов, других ограничений вроде нет. Используются маски:

>Протокол AMQP определяет 14 ~~смертных грехов~~ служебных свойств, которые будут отправлены вместе с сообщением:
> - `delivery_mode` определяет, является ли сообщение долгоживущим (*persistent*) или недолговечным (*transient*)
> - `content_type` определяет MIME-тип сообщения по аналогии с соответствующим заголовком HTTP
> - `reply_to` традиционно используется для определения названия очереди для возврата ответа (*callback queue*)
> - `correlation_id` хранит *какой-то* идентификатор. На доке `aio-pika` написано, что он удобен для сопоставления запроса с ответом (*а на какой же запрос нам пришёл ответ?*)
> - [и так далее](https://docs.aio-pika.com/apidoc.html#aio_pika.Message)

Если клиенту в очередь приходит сообщение с неизвестным `correlation_id`, это сообщение следует игнорировать, а не выкидывать ошибку, потому что есть ненулевая вероятность, что это произошло вследствие того, что:
1. сервер обработал это сообщение
2. сервер отправил результат в очередь
3. сервер умер, не успев отправить подтверждение прочтения уже обработанного запроса брокеру
4. клиент прочитал ответ и удалил его `correlaton_id` из списка "своих" идентификаторов
5. сервер ожил и увидел необработанный запрос (*опа, чирик!*)
6. сервер обработал запрос и отправил ответ, в этот раз со всеми подтверждениями
7. клиент получил ответ, но его `correlation_id` уже отсутствует в списке отслеживаемых клиентом идентификаторов, и ответ не может быть обработан, хотя формально никакой ошибки не произошло

### Publisher confirms (подтверждения публикации)
Кроличье расширение протокола AMQP, позволяющее продюсеру получать (асинхронные) уведомления о том, что сообщение было принято брокером (не было потеряно, брокер не слишком занят, чтобы его принять и т.д.)
Включено по умолчанию, за этот механизм отвечает параметр канала
```python
channel = await connection.channel(
   publisher_confirms=True,  # This is the default
)
```
Есть разные стратегии

#### Индивидуальная отправка (basically синхронная)
```python
for msg in get_messages_to_publish():
     # Waiting for publisher confirmation with timeout for every message
     await channel.default_exchange.publish(
          Message(msg),
          routing_key=queue.name,
          timeout=5.0,
     )
```

Стратегия простая, как палка. Накосячить в реализации почти невозможно. Проблема в том, что этот метод *оооочень* медленный: не больше нескольких сотен сообщений в секунду, особенно если брокер находится на другом хосте, потому что подтверждение получения сообщения брокером блокирует отправку других сообщений

#### Отправка сообщений пачками (не понял, зачем эта стратегия нужна)
Название говорит само за себя: мы отправляем сообщения пачками и ждём, когда вся пачка обработается
```python
batchsize = 100
outstanding_messages = []

# Sending the messages
for msg in get_messages_to_publish():
     outstanding_messages.append(
          asyncio.create_task(
               channel.default_exchange.publish(
                    Message(msg),
                    routing_key=queue.name,
                    timeout=5.0,
               )
          )
     )
     # Yield control flow to event loop, so message sending is initiated:
     await asyncio.sleep(0)

     if len(outstanding_messages) == batchsize:
          await asyncio.gather(*outstanding_messages)
          outstanding_messages.clear()

if len(outstanding_messages) > 0:
     await asyncio.gather(*outstanding_messages)
     outstanding_messages.clear()
```
Такая стратегия увеличивает пропускную способность больше чем на порядок (в случае с удалённым хостом), но есть проблема: мы не можем понять, что пошло не так, в случае ошибки, и для того, чтобы иметь возможность отправить сообщение заново, нужно держать всю пачку в памяти (*не совсем понял, в чём проблема. Наверное, в том, что в случае ошибки по одному объекту исключения нельзя понять, какое именно сообщение отправилось не так*).
Стратегия несколько сложнее в реализации, но позволяет увеличить пропускную способность

#### Асинхронное принятие подтверждений (вместо тысячи слов - БАЗА)
```python
# List for storing tasks
tasks = []
# Sending the messages
for msg in get_messages_to_publish():
     task = asyncio.create_task(
          publish_and_handle_confirm(
               channel.default_exchange,
               queue.name,
               msg,
          )
     )
     tasks.append(task)
     # Yield control flow to event loop, so message sending is initiated:
     await asyncio.sleep(0)

# Await all tasks
await asyncio.gather(*tasks)
```
Эта базированная стратегия не блокирует отправку новых сообщений, и мы можем использовать свою функцию, которая будет обрабатывать все события (и ошибки) процесса подтверждения сообщения:
```python
async def publish_and_handle_confirm(
    exchange: AbstractExchange,
    queue_name: str,
    message_body: bytes,
) -> None:
    try:
        confirmation = await exchange.publish(
            Message(message_body),
            routing_key=queue_name,
            timeout=5.0,
        )
    except DeliveryError as e:
        print(f"Delivery of {message_body!r} failed with exception: {)")
    except TimeoutError:
        print(f"Timeout occured for {message_body!r}")
    else:
        if not isinstance(confirmation, Basic.Ack):
            print(f"Message {message_body!r} was not acknowledged by broker!")
```
Данная стратегия позволяет добиться максимальной пропускной способности, но при её реализации легче всего накосячить

# Kafka vs RabbitMQ
## Сравнение
Kafka:
- Распределенный лог
- Высокая производительность
- Репликация данных
- Персистентное хранение
- Для стриминга данных

RabbitMQ:
- Классический брокер сообщений
- Гибкая маршрутизация
- Приоритезация
- Легковесные сообщения
- Для очередей задач

|Параметр|Kafka|RabbitMQ|
|---|---|---|
|Модель|Распределенный лог|Message Broker|
|Производительность|Высокая|Средняя|
|Маршрутизация|Простая|Сложная, гибкая|
|Репликация|Встроенная|Через плагины|
|Use Case|Big Data, Stream|Очереди задач|

Рекомендации:
- Kafka для больших объёмов данных
- RabbitMQ для классических распределенных систем
- Выбор зависит от архитектуры

# Всякая практическая херня
## Поднимаем Кафку, есть продюсер, запихиваем сообщения наши, поднимаем два или три консьюмера, которые вычитывают сообщения. Если сообщения упали в нашу Кафку, какой из консьюмеров прочитает сообщение?
- Зависит от того, сколько партиций и каким консюмерам они назначены: если партиция одна, то будет читать только один из консюмеров
- Если партиций столько же, сколько консюмеров, то будут читать все по очереди (==либо будет читать только один, если продюсер настроит отправку сообщение в конкретную партицию==)
## Kafka: один топик, три партиции, повесили двух консьюмеров. Как будет чтение?
- Один консюмер будет читать вдвое больше другого
## Мы отправляем сообщения в очередь Direct. Ее слушают два консьюмера. Кто сообщения прочтет? Оба, как в Кафка? Кто первый?
- ==По идее, будут читать по очереди, и первым будет тот, кто первым подписался
